# issue-sync-install — GitHub ↔ Jira 양방향 동기화 설치 키트

> 대상: 새 상품에 GitHub ↔ Jira 양방향 동기화(+Claude 스킬 · Slack 알림)를 붙일지 결정하고, 붙일 담당자.
> 이 문서는 **한 장 요약 + 어디를 읽을지 안내**(전달서)다. 따라 할 절차는 [adopt/](adopt/) 에, Claude 로 진행하는 스킬은 [SKILL.md](SKILL.md) 에 있다.
> 상태: 정리 2026-11-02. 근거는 **기준 상품의 운영 환경(GitHub 저장소 1 ↔ Jira 스페이스 1)에서 한 실제 시험**이다.

## 범용 스킬 예정

지금 판은 **기준 상품 한 쌍(GitHub 저장소 1 ↔ Jira 스페이스 1)에서 시험한 것**을 다른 상품에 옮겨 붙이는 키트다. 어느 상품에나 그대로 쓸 수 있는 **범용 스킬로 바꿀 예정**이다. 그 전까지 남은 일은 다음과 같다.

- **상품 전용 흐름 분리** — 이슈 등록 스킬(`files/claude/skills/report-issue/`)과 이슈 양식에 기준 상품의 화면 이식 전용 흐름(화면 구현 멈춤 양식 `screen_blocked.yml` · 적용 감사 · DS 요청)이 섞여 있다. 지금은 상품마다 [01 4절](adopt/01-바꿀-값.md#4-스킬claude-쪽--상품-종속-부분)대로 손으로 뺀다.
- **미검증 구성** — 한 스페이스에 저장소 여러 개 · 저장소 하나에 스페이스 여러 개 · 업무 유형이나 에픽 구조가 다른 스페이스 · Jira 요금제별 자동화 한도.
- **알려진 한계** — Jira 자동화에 잠금이 없어 동시 실행 때 사본이 2개 생길 수 있고, 규칙 실행이 밀린 적이 있다([6절](#6-알려진-한계--위험)).

## 쓰는 법

- 이 저장소(ai_skills)를 `.claude/skills` 에 연결했으면(저장소 [README 「스킬 설정」](../README.md#스킬-설정)) Claude Code 를 새로 열고 `/issue-sync-install` 로 부른다. 스킬이 이 폴더의 `adopt/` · `files/` 를 그대로 읽는다.
- 연결하지 않았으면 **이 폴더째**(`SKILL.md` 만이 아니라 `adopt/` · `files/` 함께) `~/.claude/skills/issue-sync-install/` 로 복사한다.
- Claude 없이 사람이 할 때는 아래 「2. 읽는 순서」대로 `adopt/` 를 따라간다.

## 폴더 구조

설치에 쓰는 것은 아래와 같다.

```
issue-sync-install/
├─ SKILL.md        설치 스킬 — adopt/02 단계 1~7 을 Claude 가 진행한다
├─ README.md       이 문서 — 한 장 요약 (전달서)
├─ adopt/          설치 안내 — 00 결정 · 01 바꿀 값 · 02 설치 순서(02a 흐름도) · 03 점검표 · 04 문제해결
└─ files/          설치에 쓰는 파일
   ├─ github/      상품 저장소의 .github/ 로 들어가는 것 전부(워크플로 · 이슈 양식 · 조립기 · 스키마) — .github/ 와 같은 모양
   ├─ claude/      상품 저장소의 .claude/ 로 들어가는 것(이슈 등록 스킬 · 별칭 명령)
   ├─ jira-rules/  Jira 자동화 규칙 5개의 템플릿과 렌더 스크립트
   └─ tools/       설치 · 검증 스크립트
```

`files/claude/skills/report-issue/SKILL.md` 는 상품 저장소에 복사해 넣는 파일이다. 이 폴더 안쪽에 있어 ai_skills 의 스킬 목록에는 나오지 않는다.

## 1. 한 장 요약

- **해 주는 것**: GitHub 이슈 또는 Jira 업무 항목 **한쪽에만** 등록하면 반대쪽 사본이 자동 생성되고, 등록 뒤 제목 · 본문 · 댓글 · 상태 · 담당 · 상위 에픽이 양쪽에 따라온다. 틀린 상위 에픽 키는 사본을 만들지 않고 Slack 으로 알린다. Claude 스킬(`/report-issue`)은 양식 · 중복 확인 · 미리보기까지 한 번에 한다.
- **구성 요소 3개**: ① GitHub Actions 워크플로 `issue-sync.yml` 1개(+ 이슈 양식 4종 · 대조표 · 본문 조립기) ② Jira 자동화 규칙 5개(**템플릿 + 렌더 스크립트**로 상품 값을 채워 가져온다) ③ Claude 스킬 + 별칭 명령(+ Slack 수신 웹후크).
- **설치 도구**: ① 값 파일 1개로 Jira 규칙 JSON 5개를 만드는 **렌더 스크립트**(`files/jira-rules/`) ② GitHub 쪽 파일을 상품 저장소에 넣는 **설치 스크립트**(`files/tools/install-files.mjs`) ③ 설치 결과가 서로 맞물리는지 보는 **검증 스크립트**(`files/tools/verify-install.mjs`) ④ 이들과 Claude · 사람의 역할 분담을 따라 단계 1~7 을 진행하는 **설치 스킬**([SKILL.md](SKILL.md)).
- **해 주지 않는 것**: 기존 이슈 일괄 이전 · 슬랙 개인 호출 · 에픽/하위 작업 동기화.
- **확인한 구성**: 저장소 1 ↔ 스페이스 1 — 운영 환경, 그리고 같은 구성의 별도 복사 환경. 그 밖의 구성(저장소/스페이스 N · 키 · 업무 유형 · 에픽 구조가 다른 스페이스)은 **미검증**이다.
- **상위 에픽**: 이슈 양식의 「상위 에픽 키」 칸은 **필수**이고, 규칙은 그 키가 스페이스에 실제로 있는 에픽일 때만 사본을 만든다.
- **되돌리기**: 워크플로·규칙을 끄면 동기화만 멈춘다. 이미 만든 사본은 남는다.

## 3. 쓰기 전에 필요한 것

Jira 스페이스 관리자(규칙 범위 변경은 전역 자동화 관리자) · **Jira 요금제의 자동화 실행 한도**(미확인) · GitHub 저장소 관리자 · 조직 Fine-grained PAT 발급(승인 필요할 수 있음) · Slack Incoming Webhooks 앱(무료 플랜 앱 10개 한도) · 팀원 PC 의 `gh` 로그인 · Atlassian 커넥터 · 설치 담당 PC 의 **Node 18 이상**(렌더 · 설치 스크립트). 자세히는 [00-결정-체크 2절](adopt/00-결정-체크.md#2-쓰기-전-필요한-것-없으면-시작하지-않는다).

## 4. 상품마다 바꿀 값 (요약)

`<SPACE>`(Jira 스페이스 키) · `<REPO>`(저장소) · Secret 이름 `JIRA_<SPACE>_WEBHOOK_URL/TOKEN` · 규칙 이름 접두사 · 에픽 기본값 `<SPACE>-0` · 대조표(사람 · 업무 유형 · 시작 날짜 필드) · 규칙의 조회 JQL · 새로 만들기 블록 · 웹 요청 7곳의 URL 과 PAT · Slack 웹후크 · 스킬의 상품명. Jira 규칙 쪽 값은 **값 파일 1개(17항목)** 로 모아 렌더 스크립트가 채운다([01 2-0](adopt/01-바꿀-값.md#2-0-값-파일--규칙-json-렌더-스크립트)). GitHub 쪽 파일의 값(스페이스 · 접두사 · 저장소 · 상품 이름 · 사이트 · 업무 유형 · 팀원 · 화면 영역)도 **값 파일 1개**로 모아 설치 스크립트가 채운다([01 1-0](adopt/01-바꿀-값.md#1-0-자동으로-넣기-install-filesmjs)). 값마다 **파일·줄·규칙·칸**은 [01-바꿀-값](adopt/01-바꿀-값.md).
짝 레이블 `gh-<저장소>-<번호>` 는 규칙이 저장소 이름에서 만들어 **바꿀 필요가 없다**.

## 5. 붙이는 순서 (요약)

규칙 렌더·가져오기(**끈 채**) → 토큰·Slack 주소 → GitHub Secret → 파일 PR 머지(`main`) → 규칙 켜기 → 스킬 → 점검표. 규칙을 먼저 켜면 웹 요청이 404 다. 자세히는 [02-설치-순서](adopt/02-설치-순서.md).
Claude Code 로 진행할 수도 있다 — 전용 스킬 `/issue-sync-install`([SKILL.md](SKILL.md) · [02 의 역할 분담](adopt/02-설치-순서.md#claude-와-함께-설치하기--역할-분담)). **Jira 화면 작업(규칙 가져오기 · 켜기) · PAT 발급 · Secret 값 입력 · Slack 앱 추가는 Claude 가 대신하지 못해** 사용자에게 한 번에 하나씩 요청한다.
🔴 **처음엔 운영과 분리된 별도 환경(복사본 저장소 · 별도 스페이스)에서** 한다. 운영 저장소에서 시험하면 서비스 버전이 오르고 운영 이슈 · Jira 에 시험 건이 남는다.

## 6. 알려진 한계 · 위험

- Jira 자동화에 **잠금이 없다** — 동시 실행에 약해 같은 요청이 겹치면 사본이 2개 생길 수 있다(수정 대안 검토 필요).
- **실행 지연**: 규칙 실행이 몇 시간씩 밀린 적이 있다(원인 확인 대기). 지연 중 규칙을 고치지 않는다.
- PAT 만료(1년 안) 시 Jira→GitHub 방향이 조용히 멈춘다(401).
- 이 PAT(Actions: write)는 같은 저장소의 다른 `workflow_dispatch` 워크플로를 부를 수 있다 — 수동 실행에 실제 배포 job 을 붙이지 않는다.
- 웹후크 주소 · 암호 · PAT 는 비밀이다. 한 번 노출돼 교체한 적이 있다.
- 스킬에는 기준 상품의 화면 이식 전용 흐름(화면 구현 멈춤 · 적용 감사 · DS 요청)이 섞여 있다 — 상품에 해당 문서가 없으면 [01 4절](adopt/01-바꿀-값.md#4-스킬claude-쪽--상품-종속-부분)대로 뺀다.

## 7. 자주 묻는 질문

| 질문 | 답 |
|---|---|
| 우리 저장소에 바로 붙일 수 있나? | 고정값을 바꾸면 된다 — [01-바꿀-값](adopt/01-바꿀-값.md). 단 시험한 구성은 저장소 1 ↔ 스페이스 1. |
| 한 Jira 스페이스에 저장소 여러 개는? | **미검증.** 짝 레이블 · 조회 JQL · Secret 이름이 저장소 1개를 가정한다 → 별도 시험. |
| Jira 요금제 제한은? | 자동화 실행·동시 실행 한도가 요금제별로 있다 — 숫자는 확인하지 못했다. 설치 전 Atlassian 문서로 확인. |
| 실패하면 어떻게 아나? | 틀린 상위 키는 Slack. 그 외는 Actions 실행(job 이름 = 방향)과 Jira 규칙 감사 로그. [04-문제해결](adopt/04-문제해결.md) |
| 이미 있는 이슈는? | 연결 전 항목은 「짝 없음」으로 건너뛴다 — 일괄 이전은 하지 않는다. |
| 스킬 없이도 되나? | 된다 — 워크플로 + 규칙만으로 양방향이 돈다. 스킬은 등록 편의(양식·중복 확인·미리보기). |
| Jira 규칙을 처음부터 손으로 만들어야 하나? | 아니다 — 템플릿 5개 + 값 파일로 JSON 을 만들어 Jira 에 가져온다(꺼진 상태). 규칙 구조를 직접 고치는 일은 이 문서의 범위 밖이다. |
| 설치를 자동화할 수 있나? | 규칙 JSON 은 렌더 스크립트, GitHub 파일은 설치 스크립트가 만든다. Jira 화면 작업과 비밀값 입력은 사람이 한다. 설치 스킬을 쓰면 값 수집 · 파일 · PR · 점검을 Claude 가 하고 사람이 할 일만 요청한다. |

## 8. 이 문서 자체의 한계

- 이 문서는 **기준 상품 한 쌍(저장소 1 ↔ 스페이스 1)에서 한 시험**을 정리한 것이다. 다른 상품에 설치했을 때의 결과는 담고 있지 않다.
- 설치 스크립트 · 스킬은 이 키트 안의 파일로 정해진 절차를 따른다. Jira 자동화 규칙의 가져오기 · 켜기, PAT 발급, Secret 값 입력은 사람이 직접 한다.
- 규칙 5개는 `files/jira-rules/` 의 템플릿과 렌더 스크립트로 만든다. 렌더 결과에는 PAT · Slack 주소 · 웹후크 암호가 없고, 내보내기 파일에는 웹후크 암호 · Slack 주소가 있어 이 저장소에 올리지 않는다.
