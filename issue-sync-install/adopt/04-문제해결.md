# 04. 문제해결 — 증상 → 먼저 볼 곳 → 원인 → 조치

> 기준 상품을 실제로 시험 · 운영하면서 **막혔던 것과 그때 해결한 방법**을 증상 기준으로 추렸다. 여기에 없는 증상은 짐작으로 고치지 않는다. 방향은 job 이름으로 안다 — `from-github` 실패 = GitHub→Jira, `from-jira` 실패 = Jira→GitHub.
> 🔴 **감사 로그가 「수행한 작업 없음」 · 「진행 중」이면 규칙을 고치기 전에 그 실행의 시각·상태를 먼저 본다** — 실행이 몇 시간 밀린 적이 있다.

## A. 설치 직후 첫 시험이 안 될 때

| 증상 | 먼저 볼 곳 | 원인 → 조치 |
|---|---|---|
| Jira 규칙 웹 요청이 **404** | 규칙 감사 로그 · URL | `main` 에 `issue-sync.yml` 이 없음(머지 전에 규칙을 켬) 또는 URL 의 저장소·파일명 오타 → 머지 확인 · URL 수정 |
| **401** | 감사 로그 | PAT 만료·오타·`Bearer ` 빠짐 → 재발급 후 **7곳 모두** 교체 |
| **403** | 감사 로그 | Actions 권한 Read-only · 토큰의 저장소 선택 밖 · 조직 승인 대기(Pending) → 토큰 권한·저장소 확인 / 조직 Pending requests |
| **422** `Unexpected inputs provided` | 규칙 본문 | 워크플로에 없는 입력을 본문에 먼저 넣음 → **워크플로 입력을 먼저 머지한 뒤** 본문에 키 추가. 입력 10개 상한이라 키를 더하려면 「a\|b」로 묶는다 |
| Actions 「Secrets … 이 없다」 | `from-github` 의 「Send to Jira automation」 | Secret 이름이 워크플로와 다름 · **Environment secrets 에 넣음**(Repository secrets 여야 함) |
| 웹후크 **400 Missing token** | 응답 본문 | 암호를 헤더 `X-Automation-Webhook-Token` 으로 안 보냄(방식 A 의 「Secret」 칸 사용) → 방식 B 사용. 감사 로그에는 안 남는다(입구 거절) |
| `github-to-jira` 규칙 암호를 바꿨는데 안 됨 | 규칙 화면 | 「규칙 업데이트」를 안 눌러 저장 안 됨 → 눌러 저장 후 Secret `…_TOKEN` 도 갱신 |

## B. 사본이 안 생길 때

| 증상 | 먼저 볼 곳 | 원인 → 조치 |
|---|---|---|
| GitHub 이슈 → Jira 사본 없음 | `from-github` 로그 「Decide kind · pair」 | 로그가 「Jira 사본 — 건너뛴다」 = 라벨 `jira` 가 붙은 이슈(정상) · Secret 비었음 · `github-to-jira` 규칙 꺼짐 · 조회 JQL 스페이스가 다름 · 새 업무 유형이 규칙 블록에 없음 |
| **상위 에픽 키를 맞게 썼는데** 사본 없음 | 「Build payload」 `epicKey` · `github-to-jira` 규칙 키 조회 | 키가 **다른 스페이스**(`^<SPACE>-[0-9]+$` 가 아니면 `null`) · 그 키가 에픽이 아님(`hierarchyLevel = 1`) · 키 조회가 「JQL 조건」으로 잘못 들어감(동작이어야 함) · 실행 대기 |
| Jira 업무 → GitHub 사본 없음 | `jira-created` 규칙 감사 로그 | 규칙 꺼짐 · 에픽(조건 통과 못함 = 정상) · 레이블 `github`(GitHub 에서 온 사본 = 정상) · 웹 요청 4xx |
| 틀린 키인데 **Slack 이 안 옴** | `github-to-jira` 규칙 감사 로그 「Slack 메시지」 | 실행 대기 · 동작이 「Slack 메시지 보내기」(앱 연결형)로 잘못 선택 · 웹후크 주소 재생성 후 규칙을 안 바꿈 · Slack 앱 한도로 Incoming Webhooks 앱이 제거됨 |

## C. 수정·댓글·상태·담당이 안 넘어갈 때

| 증상 | 먼저 볼 곳 | 원인 → 조치 |
|---|---|---|
| 수정·댓글·상태가 안 넘어감 | 「짝 없음 — 건너뛴다」 로그 | 연결 전에 만든 항목이거나 원본 끝 `<!-- jira:키 -->` 를 사람이 지움(복구: 그 표시를 다시 적는다) · 수정 · 댓글 · 상태 규칙 꺼짐 |
| 같은 건이 **두 번** 생김 | 저장소 웹훅 · `github-to-jira` 규칙 조회 | 저장소 웹훅(방식 A)이 켜져 있음 · 조회 JQL 스페이스가 사본 스페이스와 다름 · 실행이 밀린 사이 같은 요청이 동시에 돎(**알려진 한계 — 잠금 없음**) |
| 값이 오갔다 **되돌아옴(반복)** | 규칙 「허용」 · 댓글 끝 `<!-- sync:jira -->` | 「다른 규칙이 이 규칙을 트리거하도록 허용」이 켜짐 → 5개 모두 끔 · `SYNC_BOT_TOKEN` 만 넣고 `SYNC_BOT_LOGIN` 을 안 넣음 |
| GitHub 닫았는데 Jira 「완료」 안 됨 | `github-to-jira` 규칙 close 블록 | 스페이스에 「완료」 전환이 없음(유형마다 워크플로가 다름) → 전환 이름·워크플로 확인 |
| Jira 「보류」인데 GitHub 이 닫힘 | 상태 범주 | 「보류」 범주가 완료로 되어 있음 → 진행 중 범주로(워크플로는 **범주**만 본다: `done` 이 닫기) |
| GitHub 담당이 비어 있음 | `from-jira` 경고 | 대조표 `people` 에 없음 / 저장소 권한 없음(`gh api repos/<REPO>/assignees/<아이디>` 가 404) — **정상 동작**, 대조표·초대로 해결 |
| Jira 담당이 비어 있음 | `from-github` notice | GitHub 담당이 대조표에 없음 |
| Jira 상위를 바꿨는데 GitHub 키 칸이 그대로 | `jira-edited` 규칙 트리거 · `from-jira` 로그 | 트리거에 「상위」 없음 · 옛 이슈라 본문에 `### 상위 에픽 키` 칸이 없음(정상) |
| 본문 키 칸을 고쳤는데 Jira 상위 그대로 | 「Build payload」 `epicChanged` | 키가 안 바뀜 · 틀린 키(분기 B Slack) · 「상위 항목」 칸이 `{{webhookData.epicKey}}` 아님 · 「추가 옵션」에 글자가 남음 |

## D. 규칙을 만들고 고칠 때 자주 틀리는 것

| 함정 | 설명 |
|---|---|
| 「업무 항목 조회」 vs 「JQL 조건」 | 조회는 **다른 항목 검색**(동작), 조건은 **현재 항목 검사** — 혼동하면 분기가 안 탄다 |
| 복제한 분기가 같은 조회 ID 를 공유 | 복제 말고 **새로 추가** · 복제 뒤 이름·ID 확인 |
| If 분기 안에 If 불가 | 조건을 앞으로 빼거나 분기를 나눈다(edit 분기 A/B 가 이래서 둘) |
| 규칙을 복제하면 켜진 채 생김 | 바로 끈다 · 「허용」 설정도 확인 |
| 규칙 복제 시 웹후크 URL·암호가 새로 생김 | GitHub Secret 2개를 새 값으로 |
| 시험용 조회·로그 작업이 게시됨 | 게시 전에 지운다(실제로 운영에 시험 조회가 두 번 게시됐다) |
| 따옴표가 든 스마트 값(`labels.join(\",\")`) | 빈 값으로 간다 — 쓰지 않는다 |
| 담당·보고자 필드를 빈 값으로 보냄 | 값이 있을 때만 넣는다(`#if(…isNotEmpty())`) |

## E. 스킬

| 증상 | 원인 → 조치 |
|---|---|
| 「app is not installed」 403 | claude.ai ▸ Connectors ▸ Atlassian **재연결**(scopes 에 `write:jira-work`) — 토큰 캐시 파일은 읽지 않는다 |
| GitHub 이 선택지에서 빠짐 | `gh api repos/<REPO> --jq .permissions.push` 가 false/오류 → `gh auth login`·권한 |
| 저장소를 잘못 고름 | 원격이 둘이면 `gh repo view` 가 `upstream` 을 고른다 → 스킬은 `git remote get-url origin` 을 쓴다(origin 이 상품 저장소여야 함) |
| `/<상품명>:이슈등록` 이 안 보임 | 새 세션에서 `/<상품명>` 을 쳐 목록을 본다 → 별칭 명령 파일 `.claude/commands/<상품명>/이슈등록.md` 가 있는지 · 그 파일이 들어간 판을 `git pull` 로 받았는지 확인하고 **세션을 새로 연다**. 띄어 쓴 `/<상품명> 이슈등록` 은 Claude 에 **전달되지 않는다** — 콜론 형식 `/<상품명>:이슈등록` 으로 쓴다 |

## F. 확인이 안 될 때 일반 순서
1. `gh run list -R <REPO> --workflow issue-sync.yml --limit 5` → `gh run view <id> --log`(job 이름으로 방향 확인).
2. 로그의 「Decide kind · pair」(GitHub→Jira) 또는 「Check input · find pair」(Jira→GitHub)의 한 줄 요약부터 읽는다.
3. Jira 규칙 감사 로그에서 해당 실행이 「진행 중」인지 본다 — 그렇다면 기다린다.
4. 그래도 안 되면 위 1~3 에서 얻은 로그(Actions 실행 로그 · 규칙 감사 로그)를 모아 문의한다.
