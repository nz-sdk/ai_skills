# appcontext-architecture — 셸↔앱 계약(AppContext 근간) 세우기

셸(host, 여러 앱을 담는 바깥 껍데기)이 각 업무 앱 화면에게 **넘겨주는 값·기능의 묶음**이 `AppContext` 다.
이 스킬은 그 **계약(앱과 셸이 주고받는 약속)** 을 세운다. `create-frontend`(개발환경 세팅) 다음 단계다.

---

## 1. 고정 규칙

여기는 "고르는" 게 아니라 "고정되는" 규칙이다. 프로젝트가 달라도 똑같다. 각 규칙 밑에 **왜 지켜야
하는지**를 적어 뒀다 — 안 지키면 사고가 나기 때문이다.

### 1-1. 앱이 셸에 닿는 길은 두 개뿐이다.
- **설명**: 앱은 셸의 기능에 두 가지 길로만 닿는다.
  (1) 셸이 넘겨준 `AppContext`(값·기능 묶음),
  (2) `@desktop/sdk` 같은 공용 도구를 직접 가져다 쓰기. 셸의 속(내부 코드)은 **직접 만지지 못하게** 막는다.
  그래야 나중에 셸을 고쳐도 앱이 안 깨진다.
- **규칙**: 앱에 노출하는 층은 A(주입 `AppContext`, plain 객체) + B(SDK 배럴, 직접 import — 타입·무상태
  도구)뿐. C(셸 내부 hooks)는 경계 아래 — 앱이 직접 import 금지(§1-3 grep 로 강제).

### 1-2. "주입"에 둘지 "배럴"에 둘지는 규칙으로 정해진다.
- **설명**: 값 하나를 앱에 줄 때, **바뀌면 화면이 저절로 다시 그려져야 하는 값**(테마·언어·로그인 사용자)은
  "주입"으로 준다. **안 바뀌는 도구나 타입**(날짜 포맷 함수, 타입 등)은 "배럴"로 준다. 이건 **취향이 아니라
  값의 성질**이 정한다 — 그래서 AI 가 규칙대로 자동 분류하고, 사용자에게 묻지 않는다.
- **규칙**: 판별 규칙 — *"바뀌면 화면 리렌더 필요? 예 → 주입 / 아니오(도구·타입·공유 인스턴스) → 배럴."*
  아래 표는 이 규칙을 참조 구현(nz-web)에 적용한 **예시**다(보편 목록 아님 — 새 프로젝트는 자기 표면에 규칙을 적용):

  | 표면 | 주입/배럴 |
  |---|---|
  | `theme`·`locale`·`user` (+세터) | 주입 (바뀌면 화면 갱신) |
  | `openApp`·`widgets`·`settings` | 주입 (동작·상태) |
  | `comms` | 주입 + 배럴 (둘 다 — 같은 한 벌) |
  | i18n 헬퍼·`format*`·타입 | 배럴 (안 바뀌는 도구) |

### 1-3. 앱은 셸 속을 직접 만지지 않는다 · 라이브러리는 한 벌만 공유
- **설명**: 앱이 주소·통신·i18n·셸 내부 파일을 **직접** 건드리면 안 된다(계약으로만 닿아야 함).
  또 react 같은 라이브러리를 앱이 따로 한 벌 더 가지면 **상태가 두 벌**이 되어 화면이 조용히 어긋난다 —
  그래서 공용으로 **한 벌만** 나눠 쓴다.
- **규칙**: 앱 폴더에서 아래 grep 이 **전부 0건**(셸 내부 import 는 타입만):
  ```bash
  grep -rn "location\.\|history\."  src/apps/    # 주소는 context.route 만
  grep -rn "fetch(\|new WebSocket"  src/apps/    # 통신은 SDK 만
  grep -rn "i18n.init"              src/apps/    # i18n 재초기화 금지
  grep -rn "from '@/shared\|from '@/components/shell" src/apps/  # 셸 내부 직접 import 금지
  ```
  `react`·SDK·UI 부품·i18n·계약 Context 는 공유 목록(external)에 넣는다.

### 1-4. 다른 화면을 열 때는 `openApp` 을 쓴다 (앱이 주소를 직접 안 만짐)
- **설명**: 앱이 다른 화면(또는 자기 다른 화면)을 열 때는 `openApp` 이라는 정해진 함수를 쓴다. 앱이
  브라우저 주소를 직접 바꾸지 못하게 해서, "주소는 셸이 관리한다"는 약속을 지킨다.
- **규칙**: `openApp(id, params?)`. 딸린 값은 `launchParams`(이번 열기용 — 주소에 안 들어가 새로고침하면
  사라짐), 재열림 신호는 `launchNonce`. (주소를 *쓸지 말지* 자체는 3-4.)

### 1-5. 앱은 화면을 `default` 로 내보낸다 · 화면 엔진은 셸 하나뿐 (엔진 1개 고정)
- **설명**: 앱은 자기 화면을 `default` 로 내보내기만 하고, **그리기는 셸이 한다.** 앱이 자기 화면 그리기를
  따로 시작하면(엔진 2개) 예전에 사고가 났다 — `mount` 라는 말이 "붙일 것"과 "함수 이름" 두 뜻으로 읽혀
  앱이 자기 엔진을 켰고, 화면 엔진이 2개가 되어 문제가 생겼다. 그래서 **엔진은 셸 1개로 고정**한다.
- **규칙**:
  ```ts
  // src/apps/<id>/index.ts
  export default function App(props: AppComponentProps) { /* 화면 */ }
  // AppModule = { default: ComponentType<AppComponentProps>; widgets?; settings? }
  ```
  `mount` 라는 코드체 낱말 금지(함수를 뜻하면 시그니처와 함께 쓸 것). 엔진 2개(앱이 자기 `createRoot`)는
  **묻지 않고 쓰지 않는다** — 정말 완전 격리가 필요하면 이 계약 범위 밖(iframe 등)이며, 굳이 쓰려면 팀이
  CLAUDE.md 에 이유를 적고 이탈(비상구).

## 2. 조건부 규칙 — 셸이고 앱을 따로 배포할 때만

- **설명**: 앱을 셸과 **따로 배포**(나중에 앱만 따로 올림)하는 경우에만 아래 셋이 필요하다. 앱을 셸에 **같이
  넣어** 한 번에 빌드하면(자기완결) 이 절은 통째로 건너뛴다 — 따로 안 배포하니 필요 없다.
- **규칙**(`create-frontend §1-0 = 셸` **이고** 배포 형태 = 따로(catalog) 일 때만):
  - **앱 로딩** — dev 는 소스 직접 로드(L1), prod 는 카탈로그의 외부 URL 로드(L3).
  - **버전 게이트** — 앱의 `sdkVersion` 이 셸의 `SDK_VERSION` 보다 크면 로딩 거부("빌드는 되는데 실행이 죽는" 것 방지).
  - **SRI** — 앱 파일 지문(SHA-384)을 검증한 뒤 실행. 검증 도구(`crypto.subtle`)가 없는 환경(평문HTTP·사설IP)이면 검증 건너뛰고 일반 로드(폴백 필수).

## 3. 프론트 인터페이스 아키텍처 결정 (앱 소스·경계·화면 배치·주소·계약 표면)

여기는 프론트 인터페이스 아키텍처에서 **프로젝트마다 답이 다른(=결정하는) 부분**이라, AI 가 추측하지 않고 **반드시 물어서** 정한다.
각 선택: 물어보고 → 답을 프로젝트 CLAUDE.md 에 `(a)채택 / (b)근거 / (c)뒤집힐 조건` 으로 적고 → 그 답대로 적용.

### 3-1. 앱 소스·팀 모델 — 앱을 누가·어디서 만드나 (가장 먼저)
- **설명**: 업무 화면(앱)을 **우리 팀이 직접** 만드는지, **다른 팀/개발자가** 우리 껍데기(셸)를 받아서 만드는지 정합니다. 이게 앞으로 작업이 어느 저장소(레포)에서 돌아가는지를 정하기 때문에 제일 먼저 묻습니다.
- **`AskUserQuestion`** (header: `앱 소스`) — 물음: *"이 앱들을 누가, 어디서 만듭니까?"*
  - **우리 팀이 한 레포에서 만든다** — 앱을 셸과 같은 저장소 안에서 우리가 직접 만든다.
  - **다른 개발자가 셸을 받아서 만든다** — 다른 팀이 우리 셸을 받아 앱을 만든다. 우리가 정한 규칙은 셸과 함께 전달되고, 받은 쪽은 그 규칙을 바꾸지 않는다.

### 3-2. 앱 경계 — 앱 하나를 얼마나 잘게 나누나
- **설명**: "앱 하나"의 크기를 정합니다. 메뉴 하나하나를 각각 앱으로 잘게 나눌 수도, 관련 메뉴들을 묶어 "시스템 하나 = 앱 하나"로 굵게 만들 수도 있습니다.
- **`AskUserQuestion`** (header: `앱 경계`) — 물음: *"앱 하나의 크기는 어느 쪽입니까?"*
  - **잘게 (메뉴 하나 = 앱 하나)** — 메뉴마다 앱이 따로다. 앱 개수가 많아진다.
  - **굵게 (시스템 하나 = 앱 하나)** — 관련 메뉴들을 한 앱으로 묶고, 메뉴는 그 안의 화면이 된다. 앱 수가 적다.

### 앱 엔진 — 묻지 않는다 (엔진 1개로 고정)
- **설명**: 화면을 그리는 "엔진"을 몇 개로 할지는 §1-5 에서 이미 **하나로 고정**했습니다(둘이면 예전에 사고가 났음). 그래서 여기서는 **묻지 않습니다.**
- **적용**: 선택 아님. §1-5 그대로.

### 배포 형태 — 묻지 않는다 (create-frontend 값을 읽음)
- **설명**: 셸(여러 앱 껍데기)로 갈지, 자기완결 앱 하나로 갈지는 앞 단계(create-frontend)에서 이미 정했습니다. 그 값을 읽어서 씁니다.
- **적용**: `create-frontend §1-0` 기록값 사용. 앱을 따로 배포하면 §2(조건부 규칙)를 켠다.

### 3-3. 동시 화면 — 여러 화면을 한 번에 나란히 놓고 쓰나
- **설명**: 일하는 사람이 화면을 **한 번에 하나만** 보면 되는지, **두 개 이상을 나란히** 놓고 봐야 하는지 정합니다. (창·탭·분할 같은 **겉모양은 이 스킬이 정하지 않습니다** — 디자인에서 정함.)
- **`AskUserQuestion`** (header: `동시 화면`) — 물음: *"화면을 한 번에 두 개 이상 나란히 놓고 봐야 합니까?"*
  - **여러 개 나란히 본다** — 화면 두 개 이상을 동시에 띄운다. (예: 왼쪽 화면 보면서 오른쪽 화면도 같이 확인.) 셸이 그 배치를 맡는다.
  - **한 번에 하나만 본다** — 화면을 하나씩만 본다. 더 단순하다.

### 3-4. 주소 — 링크·새로고침으로 화면이 유지되나
- **설명**: 특정 화면을 **링크(주소)로 바로 열 수 있게** 하고, **새로고침해도 그 화면이 그대로 남게** 할지 정합니다.
- **`AskUserQuestion`** (header: `주소`) — 물음: *"링크로 특정 화면을 바로 열거나, 새로고침해도 그 화면이 남아야 합니까?"*
  - **유지된다 (주소 씀)** — 링크로 화면을 보내줄 수 있고, 새로고침해도 화면이 그대로다.
  - **유지 안 됨 (안 씀)** — 새로고침하면 열린 화면이 사라지고 처음으로 돌아간다.

### 3-5. 계약 표면 — 앱에 어떤 기능 자리를 열까 (반드시 정한다)
- **설명**: 계약이 앱에게 열어줄 "기능 자리"를 고릅니다. 기본 자리는 항상 넣고, 나머지는 필요한 것만 고릅니다. 계약은 **자리만** 열고, 실제 기능은 나중에 상품팀이 만듭니다.
- **`AskUserQuestion`**:
  - **기본 자리(항상 넣음)** — 테마 · 언어 · 다른 화면 열기 · 로그인 사용자 · 통신. 대부분의 앱이 쓰는 최소 세트라 항상 넣는다. *(코드: `theme`·`setTheme`·`locale`·`localePreference`·`setLocale`·`openApp`·`user`·`comms`. `windowId` 는 3-3 에서 셸 배치 관리 시 붙음.)*
  - **추가 자리** (`AskUserQuestion` · 여러 개 선택 가능 · header: `표면`) — 물음: *"기본 외에 열어둘 기능 자리를 고르세요(안 골라도 됨)."*
    - 위젯·설정(홈 위젯·앱 설정 패널 — 프로젝트마다 쓸 수도 안 쓸 수도) · 앱 내부 주소·창 배치·홈 복귀 · 알림·일정 · 검색·알림설정 · 원격·구독 *(코드: `widgets`·`settings` · `route`·`windows`·`exit` · `reminders`·`calendar`·`push` · `search`·`notificationSettings` · `isRemote`·구독)*
  - 고른 자리만 계약에 넣는다. 실제 기능 구현은 넣지 않는다.
  - **위젯·설정을 골랐을 때만**: "무엇이 있는지 목록"은 앱을 안 열고도 알 수 있게 따로 두고, 실제 화면은 그릴 때 가져온다. 안 골랐으면 이 규칙은 없다.

> **참고**: 언어/테마 전환 **버튼을 어디 그리나**는 이 계약이 다루지 않는다(계약엔 `theme`·`locale` 값만 있음).
> 버튼 위치는 하류 UI 결정이라 DS 부품으로 처리한다.

## 4. 조립과 프로바이더 트리 — 선택을 받아 계약을 실제로 만든다

여기는 §3 에서 고른 답을 받아 **AppContext 를 실제로 조립하고 프로바이더 트리에 배치**하는 단계다.
뼈대(트리 모양·조립 방식·셸 훅 양식)는 §1 이 정해 **고정**이고, §3 선택은 트리에 층을 더하지 않고
**계약 값(필드)만** 켜고 끈다.

### 4-1. 조립 양식 — 계약을 한 곳에서 한 객체로 만든다
- **설명**: 셸이 앱에게 줄 값·기능을 **한 파일 한 곳에서** 한 덩어리로 모아 만든다. 여러 곳에서 만들면
  자리를 하나 더할 때마다 여러 곳을 맞춰야 하고, 한 곳이 빠지면 조용히 어긋난다. 그래서 조립은
  **한 곳**으로 고정한다.
- **규칙**: 셸에 조립 컴포넌트 하나(예: `AppContextRoot`)를 두고, 그 안에서 `AppContext` 타입으로 객체
  하나를 만들어 Provider 로 내려보낸다. TS 가 타입을 강제하므로 자리 하나라도 빠지면 컴파일이 실패한다.
  *(아래 이름은 참조 구현 예시 — 구조가 규칙이다.)*
  ```tsx
  function AppContextRoot({ children }) {
    const { theme, setTheme } = useTheme()                       // 셸 훅 — 값(4-3)
    const { locale, localePreference, setLocale } = useLocale()  // 셸 훅 — 값(4-3)
    const context = useMemo<AppContext>(() => ({
      theme, setTheme, locale, localePreference, setLocale,      // 기본 자리(항상)
      openApp: (id, ...a) => openApp(id, ...a),
      user: getCurrentUser(), comms: client,
      // 3-3 켰으면  windows: windowsApi,
      // 3-4 켰으면  route: { get, set, subscribe, launchNonce, subscribeLaunch, launchParams },
      // 3-5 추가 선택만  widgets, settings, …
    }), [theme, setTheme, locale, localePreference, setLocale])  // ← 값만 deps(4-2)
    return <AppContextProvider value={context}>{children}</AppContextProvider>
  }
  ```

### 4-2. 값 종류별 배선 — deps 에 넣을지 규칙으로 가른다
- **설명**: 조립할 때 각 자리를 **어떻게** 채우는지 규칙이 있다. 바뀌면 화면을 다시 그려야 하는 것
  (테마·언어)은 **값**으로 담고, 자주 바뀌지만 화면을 다시 그릴 필요 없는 것(주소·창·번호표)은
  **읽는 함수+구독**으로 담는다. 안 그러면 창 하나 열 때마다 계약이 통째로 새로 만들어져 화면이
  전부 다시 그려진다.
- **규칙**:
  | 자리 | 채우는 법 | `useMemo` deps |
  |---|---|---|
  | 테마·언어(+세터) | 셸 훅에서 **값**(4-3) | **넣는다** |
  | 주소·창·번호표 | **읽는 함수 + 구독**(get/subscribe) | 뺀다 |
  | 사용자·통신·위젯·설정 | 모듈 싱글턴/고정값 | 뺀다 |

  앱 쪽은 자주 바뀌는 것을 `useSyncExternalStore(subscribe, get)` 로 읽는다.

### 4-3. 셸 훅 양식 — 값 담는 주입 표면의 상태 저장소 (틀은 고정)
- **설명**: 테마·언어처럼 **값을 담는 주입 표면**은 셸이 그 값을 어딘가 들고 있어야 한다. 그 저장소가
  **셸 훅**이다(테마 = `useTheme`, 언어 = `useLocale`). **앱은 이 훅을 import 하지 못하고 계약으로만
  받는다**(경계). 어떤 표면이 셸 훅을 갖는지는 **규칙으로 정해진다**(따로 고르지 않음): "값을 담는
  주입 표면"마다 셸 훅 하나. 주소·창처럼 함수+구독으로 담는 것은 셸 훅이 아니라 모듈 스토어다.
- **규칙**:
  - **상태 도구는 React Context 로 고정**한다(다른 상태 라이브러리 안 씀 — create-frontend 가 React).
  - **공통 로직은 템플릿에서 import 한다**(고정) — 저장소 읽기/쓰기·JSON·예외처리(샌드박스 throw)·
    lazy init 은 `templates/local-storage.ts`(이 스킬에 동봉) 에 **한 번 써두고 가져다 쓴다**. 스킬 실행
    시 이 파일을 새 프로젝트로 복사하고(예: `src/hooks/lib/`), 얇은 셸 훅이 `usePersistentState` 를
    import 한다. **AI 는 이 공통 로직을 다시 작성하지 않는다**(임의 방지). 셸 내부 util 이라 앱은 import
    하지 않는다(external·CSP 무관).
  - **셸 훅은 얇게** — 표면별 부분만 직접 쓴다: 테마 = `html.dark`·모듈 로드 시 1회 적용(FOUC 방지) /
    언어 = i18next 거울·`html lang`. 이 부분은 공통이 아니다.
  - **양식(고정 틀)** — Context + Provider(상태 보유) + `useHook()`(밖에서 부르면 throw) +
    안정 세터 + `useMemo` value. 형(型)은 규칙으로:
    - **state형** — 값의 **진실이 셸 안**일 때(테마) → `usePersistentState`(템플릿) 사용.
    - **거울형** — 값의 **진실이 밖 공유 인스턴스**일 때(언어=i18next, 사용자=인증 SDK) →
      `useSyncExternalStore` 로 구독(저장은 그 인스턴스가). *`usePersistentState` 를 값에 쓰지 않는다.*
    - 어느 형인지는 **취향이 아니라 "진실이 어디 있나"가 정한다.**
  ```tsx
  // 공통(템플릿) — templates/local-storage.ts (이 스킬에 동봉)
  export function usePersistentState<T>(key, initial, validate): [T, (n: T) => void]  // 저장소+lazy+예외

  // 얇은 셸 훅 — src/hooks/use-theme.ts (state형)
  const isTheme = (r: unknown): r is Theme => r === 'light' || r === 'dark'
  function ThemeProvider({ children }) {
    const [theme, setTheme] = usePersistentState('desktop:theme', 'light', isTheme)   // ← 공통에서
    React.useEffect(() => {                                                            // ← 표면별(테마만)
      document.documentElement.classList.toggle('dark', theme === 'dark')
    }, [theme])
    const value = React.useMemo(() => ({ theme, setTheme }), [theme, setTheme])
    return <ThemeContext.Provider value={value}>{children}</ThemeContext.Provider>
  }
  function useTheme() { const c = React.useContext(ThemeContext); if (!c) throw new Error('…'); return c }
  ```

### 4-4. 빈칸은 미리 정한다 — AI 가 지어내지 않게
- **설명**: 위 양식(틀)은 고정이지만, 틀 안의 **몇몇 값(빈칸)** 은 규칙으로 안 정해진다. 이 빈칸을 미리
  정해 프로젝트 CLAUDE.md 에 적어두지 않으면 **AI 가 알아서 채운다(=임의 작성)**. 그래서 **빈칸은
  먼저 정해 적는다.** 이게 이 스킬의 "AI 가 추측하지 않는다"를 셸 훅까지 지키는 방법이다.
- **규칙**: 아래 빈칸은 셸 훅을 만들기 **전에** 정해 CLAUDE.md 에 적고, AI 는 **적힌 값만** 쓴다:
  | 빈칸 | 잠그는 법 |
  |---|---|
  | 저장 키·훅 이름 | 프로젝트 값으로 확정(예: `<접두어>:theme`). AI 가 이름을 짓지 않는다 |
  | 기본값(첫 화면 밝게/어둡게 등) | 프로젝트 값으로 확정 |
  | 진실 공급원이 아직 없는 표면(예: `user` 의 인증 방식) | 정해질 때까지 **계약에 올리지 않고 보류**. 추측으로 state형/거울형을 정하지 않는다 |
  - 정리: **빈칸이 안 정해졌으면 지어내지 말고 → (a) 사용자에게 묻거나 (b) 그 표면을 보류**한다.

### 4-5. 프로바이더 트리 — 뼈대는 고정, 선택은 필드만 바꾼다
- **설명**: 화면 엔진은 셸 하나(§1-5)다. 그 하나의 트리 안에 프로바이더를 쌓고, **맨 안쪽에 계약
  조립(4-1)** 을 두어 앱·위젯이 그 아래에서 계약을 물려받는다. §3 선택은 이 트리에 **층을 더하지
  않는다** — 실리는 필드만 바뀐다.
- **규칙**: 트리 뼈대(고정) —
  ```
  createRoot ──── 하나뿐 (셸 진입, §1-5)
  └ 오류 경계 ─── 맨 바깥(프로바이더가 터져도 잡음)
    └ [인증 프로바이더] ─ 쓰면
      └ 테마 프로바이더 ┐  ← 계약이 이 값을 읽으므로
        └ 언어 프로바이더 ┤    반드시 조립보다 **바깥**
          └ [공용 프로바이더(Tooltip 등)]
            └ 셸 크롬(홈·라우팅)
              └ AppContextRoot ──── 계약 1곳 조립(4-1)
                └ AppContextProvider value={context}
                  ├ 홈 위젯 (useAppContext())
                  └ 앱 자리 → 오류 경계(앱만) → <App context={context}/>
                                     (앱은 셸 프로바이더 전부 물려받음)
  ```
  - **고정**: createRoot 하나 · 계약 조립 한 곳 · Provider 하나 · 앱은 그 아래(물려받음) ·
    테마·언어 셸 훅 프로바이더는 조립보다 **바깥**(조립이 그 값을 읽으므로).
  - **프로젝트가 정함**: 어떤 프로바이더가 몇 개(인증·공용부품 등)·순서.

## 6. 결과를 프로젝트 CLAUDE.md 에 기록한다 (create-frontend 와 같은 파일)

- 이 결과는 **create-frontend 가 만든 그 프로젝트 CLAUDE.md 에 이어서** 적는다(새 파일이 아니라
  같은 파일). create-frontend 가 개발환경(배포형태·프레임워크·폰트 등)을 적어 뒀으니, 이 스킬은 그 아래에
  **"계약(AppContext) 근간" 섹션**을 더한다. **사용자가 고른 선택뿐 아니라 §1·§2 고정 규칙·§4 양식도 함께** 적어야,
  다음 사람이 읽고 계약 전체를 안다. AI 가 알아서 적으니 사람이 따로 채울 것은 없다.
- **기록**: 프로젝트 CLAUDE.md 의 "계약 근간" 섹션에 아래를 적는다(create-frontend 가 이미 적은 배포형태 등은 중복하지 말고 참조):
  1. **고정 규칙(§1)** — 계약 3층위 · 주입/배럴 판별 규칙 · 경계·단일 인스턴스 · `openApp` 딥링크 · 진입점 = `default`(엔진 1개 고정, `mount` 금지).
  2. **조건부 규칙(§2)** — 셸+따로 배포면 앱로딩·버전게이트·SRI 를 적용했다고 기록(자기완결이면 "해당 없음").
  3. **고른 선택(§3-1~3-5)** — 팀모델·앱경계·동시화면·주소·계약 표면(연 표면 목록). 각 선택은 `(a)채택 / (b)근거 / (c)뒤집힐 조건` 3줄.
  4. **조립·셸 훅 빈칸(§4)** — 셸 훅의 저장 키·기본값·훅 이름을 확정해 적어 AI 가 지어내지 않게 하고, 진실 공급원이 안 정해진 표면은 "보류"로 표시한다.
  5. **프로젝트 값** — 포트·도메인·로케일·모듈명 등.
- 이후 앱을 만드는 작업은 이 기록을 읽어서 따르고, 같은 걸 다시 묻지 않는다.
