# 01. 바꿀 값 — 기준 상품 ↔ EXP 고정값을 내 상품 값으로

> 새 상품에 붙일 때 **치환할 값 전수**다. 기준 소스는 이 키트의 `files/` — 운영 저장소(`<소유자>/<기준 저장소>`)의 `.github/` · `.claude/skills/report-issue/` 와 같다. 단 이슈 양식(`github/ISSUE_TEMPLATE/*.yml`)의 스페이스 키 자리는 `<<SPACE>>` 로 비워 두었고, 대조표(`github-jira-map.yml`)는 예시 파일 없이 `install-files.mjs` 가 값 파일로 만든다. 옮길 때는 `install-files.mjs`(1-0절)를 쓴다.
> 아래 표의 「위치」는 이 문서를 쓴 시점의 줄 번호다. 줄이 밀렸으면 **값으로 grep** 한다: `grep -rnE "<기준 값1>|<기준 값2>|…" <옮긴 파일들>` — 「기준 값」은 아래 0절 표의 「기준 상품의 값」 열(스페이스 키 · 저장소 이름 · 소유자 · 사이트 · cloudId 앞자리 · 규칙 접두사 · 상품 한글 이름) — 결과가 아래 표에 없는 줄이 나오면 이 문서의 누락이다(알려 달라).

## 0. 먼저 정할 상품 값 (표 맨 위 빈칸 채우기)

| 이름 | 기준 상품의 값 | 내 상품 값 | 이름 규칙 |
|---|---|---|---|
| `<SPACE>` Jira 스페이스 키 | `EXP` | | 대문자 · 숫자 2자 이상(워크플로 정규식 `[A-Z][A-Z0-9]+`) |
| `<REPO>` GitHub 저장소 | `<소유자>/<기준 저장소>` | | `소유자/이름` |
| `<SITE>` Jira 사이트 | 기준 상품이 쓰는 사이트 주소 | (같은 회사면 그대로) | `https://` 없이 `<이름>.atlassian.net` 형식 |
| `<CLOUD_ID>` Jira cloudId | 기준 상품의 cloudId(대조표 `jira.cloudId`) | (같은 사이트면 그대로) | Atlassian MCP `getAccessibleAtlassianResources` 로 얻는다 |
| `<PREFIX>` Jira 규칙 이름 접두사 | `[기준]` | | 목록에서 다른 상품 규칙과 구별되면 된다. 예 `[ABC]` |
| `<EPIC0>` 없는 키 기본값 | `EXP-0` | `<SPACE>-0` | 존재하지 않는 키여야 한다 |
| `<SECRET_URL>` · `<SECRET_TOKEN>` | `JIRA_EXP_WEBHOOK_URL` · `JIRA_EXP_WEBHOOK_TOKEN` | `JIRA_<SPACE>_WEBHOOK_URL` · `…_TOKEN` | 워크플로와 **글자 그대로** 같아야 함 |
| `<SLACK_CHANNEL>` | `#exp-지출증빙프로젝트` | | 알림 받을 채널 |
| `<상품명>` 스킬 별칭 | 기준 상품의 한글 이름 (명령 `/<상품명>:이슈등록`) | | 명령 폴더 이름 = 네임스페이스. 같은 세션에 두 상품이 있어도 겹치지 않는 이름 |

### 0-1. 값을 어떻게 확인하나 (Atlassian MCP · 읽기만)

| 알아낼 값 | 방법 |
|---|---|
| 스페이스의 **업무 유형 이름** (대조표 `issueTypes` · 규칙 새로 만들기 블록) | `getJiraProjectIssueTypesMetadata`(스페이스 키) — 유형 이름 · 계층 레벨(에픽 = 1 · 일반 = 0 · 하위 작업 = -1) |
| 「시작 날짜」 필드 id (`customfield_…`) | `getJiraIssueTypeMetaWithFields`(스페이스 · 유형) 에서 「시작 날짜/Start date」 필드. **없으면 대조표 `startDateField` 줄 삭제 + 규칙 추가 필드 JSON 의 `customfield_…` 줄 삭제** |
| 「완료」 · 「할 일」 **전환 이름**, 상태 범주 | 그 스페이스 업무 1건에 `getTransitionsForJiraIssue` — `github-to-jira` 규칙 close/reopen 블록의 전환 이름과 같아야 한다. 완료 상태의 범주가 `done` 인지 상태 설정에서 확인 |
| 팀원 `jiraAccountId` | `lookupJiraAccountId` — 대조표 `people` 에 쓴다(이메일은 쓰지 않는다) |
| `<EPIC0>` 가 정말 없는 키인지 | `getJiraIssue`(`<SPACE>-0`)가 없음 오류여야 한다 |
| 에픽이 레벨 1 인지 | 위 유형 조회에서 에픽의 계층 레벨 |
| 프로젝트 id (`PROJECT_ID`) | `getVisibleJiraProjects` 결과에서 키 `<SPACE>` 행의 `id`(숫자) |
| 업무 유형 id (`ISSUE_TYPE_ID_*`) | `getJiraProjectIssueTypesMetadata` 결과의 유형별 `id` — 「기능」 유형이 없으면 `ISSUE_TYPE_ID_FEATURE` 에 작업의 id |
| cloudId (`CLOUD_ID`) | `getAccessibleAtlassianResources` |
| 소유자 accountId (`OWNER_ACCOUNT_ID`) | `atlassianUserInfo`(본인) 또는 `lookupJiraAccountId` |
| 앱 계정 id (`ACTOR_ACCOUNT_ID`) | 같은 사이트의 기존 규칙을 내보낸 파일의 `actor.value`(「Automation for Jira」 앱 계정). 그 파일은 저장소에 올리지 않는다 |

### 0-2. 스페이스에 「기능」 유형이 없을 때

- 대조표 `issueTypes.Feature` 를 **「작업」**(그 스페이스에 있는 유형)으로 바꾼다. `Bug`·`Task` 도 그 스페이스의 실제 이름으로.
- `github-to-jira` 규칙 새로 만들기 3블록 중 **「기능」 블록**: 지우거나, 그 블록의 유형을 「작업」으로 바꿔 두 블록이 같게 한다(`If jiraType = 기능` 은 대조표가 「작업」을 내보내면 타지 않는다).
- 스페이스에 대조표에 없는 유형이 더 있어도(예: 스토리) `jira-created` 규칙는 레벨 0 이면 모두 GitHub 으로 넘긴다. GitHub Type 은 `issueTypes` 에 없으면 버그/Bug → Bug · 기능/Feature → Feature · 그 밖 → Task 로 정해진다(`issue-sync.yml` 의 `gtype_of`). 의도와 다르면 `issueTypes` 에 그 유형을 더한다.

### 0-3. 상위 에픽을 쓰지 않는 스페이스

이 방식은 **상위 에픽을 전제**로 한다 — GitHub 양식 「상위 에픽 키」 칸이 필수(`required: true`)이고, `github-to-jira` 규칙이 `project = <SPACE> AND hierarchyLevel = 1 AND key = "<키>"` 로 찾아 **1건일 때만** 사본을 만든다. 에픽이 없으면 GitHub 에서 어떤 이슈를 올려도 사본이 생기지 않고(Slack 알림만) 시험을 시작할 수 없다. 설치 전에 `project = <SPACE> AND hierarchyLevel = 1` 로 에픽 수를 센다([00](00-결정-체크.md) 2절 · 5절 질문 3).

| 선택 | 방법 | 상태 |
|---|---|---|
| ⓐ 기본 에픽 | 스페이스에 에픽 1개(예 「일반」 · 「시험용 에픽」)를 만들고 모든 이슈의 상위 키로 그 키를 쓴다. 코드 변경 없음 | — |
| ⓑ 에픽 선택 사항 | 양식 칸을 필수 아님으로, 워크플로 `epicKey` 검사와 `github-to-jira` 규칙의 키 조회·「사본 안 만듦」 분기를 「키가 비면 상위 없이 만든다」로 고친다 | **미검증** — 코드·규칙 변경이라 이번 범위 밖. 하려면 별도 시험 계획 |

> **바꾸지 않아도 되는 것(오해 주의)** — 짝 레이블 `gh-<저장소 이름>-<번호>` 는 규칙이 `{{webhookData.repository.name}}` 로 만든다. 저장소 이름이 바뀌면 자동으로 따라가므로 손대지 않는다.

## 1. GitHub 쪽 — 파일

### 1-0. 자동으로 넣기 (`install-files.mjs`)

이 절의 1-1 ~ 1-4 와 4절의 스킬 치환은 **스크립트로 한 번에** 할 수 있다 — 손으로 하지 않아도 된다.

1. `files/tools/install-values.example.json` 을 **저장소 밖**에 복사해 값(스페이스 · 접두사 · 저장소 · 상품 이름 · 작성자 ID(선택) · cloudId · 사이트 · 업무 유형 이름 · 시작 날짜 필드 · 팀원 · 화면 영역)을 채운다. 접두사 · 스페이스는 Jira 규칙 값 파일(2-0절)과 **같아야** 한다.
2. `node files/tools/install-files.mjs --values <값 파일> --target <상품 저장소> --dry` 로 미리 보고, `--dry` 를 빼 실행한다.
3. 파일 11개(워크플로 · 양식 5 · 조립기 · 스키마 · 대조표 · 스킬 · 별칭)를 복사하며 기준 상품 글자를 값으로 바꾼다. **기준 상품 글자가 남으면 쓰지 않고 실패**하고, 이미 있는 파일은 덮어쓰지 않는다(`--force` 로만).
4. 값 형식이 틀리면(스페이스 키 · UUID · 계정 id · 영역 이름 · 팀원 목록에 없는 후보 등) 이유를 적고 멈춘다.

스크립트가 **하지 않는 것**: `ci.yml` 수정(1-5) · 「화면 구현 멈춤」 정리(1-3 · 4절) · 커밋 · push. 아래 1-1 이하 표는 그 부분과 직접 확인할 때 쓴다. 자체 시험: `node files/tools/install-files.mjs --selftest`.

설치 뒤에는 **맞물림 검사** `node files/tools/verify-install.mjs --target <상품 저장소> --rules-out <규칙 출력 폴더> --repo <REPO> --deep` 를 돌린다 — 스페이스 키 · Secret 이름 · 규칙 이름 접두사 · 웹 요청 대상 · 워크플로 입력 이름 · 규칙이 읽는 값 · 업무 유형 이름 · 시작 날짜 필드 · 이슈 양식 · 스킬 별칭이 서로 어긋나지 않는지 본다(`--deep` 은 YAML 문법과 대조표 스키마까지).

## 2. Jira 쪽 — 자동화 규칙 5개 (스페이스 범위)

규칙 5개는 **템플릿 + 렌더 스크립트**(`files/jira-rules/`)로 만든다 — 2-0 의 값 파일 하나로 아래 칸이 모두 채워진다. 내보내기 파일에는 웹후크 암호 · Slack 주소가 있으니 **저장소에 올리지 않는다**.

규칙 5개는 아래 이름으로 부른다. **이름 = 템플릿 파일 이름**(`files/jira-rules/templates/<이름>.template.json`)이고, Jira 목록에는 앞에 `<PREFIX>` 가 붙은 이름으로 보인다.

| 이름(템플릿 파일) | Jira 에 보이는 규칙 이름 | 하는 일 |
|---|---|---|
| `github-to-jira` | `<PREFIX> Github -> Jira Issue` | GitHub 이슈의 등록 · 수정 · 댓글 · 닫기/다시 열기 · 담당을 수신 웹후크로 받아 Jira 에 반영한다 |
| `jira-created` | `<PREFIX> Jira -> Github Issue` | Jira 에서 만든 일반 업무(레벨 0)를 GitHub 이슈 사본으로 만든다 |
| `jira-edited` | `<PREFIX> Jira 수정 -> Github Issue` | Jira 의 요약 · 설명 · 담당 · 상위 변경을 GitHub 에 반영한다 |
| `jira-comment` | `<PREFIX> Jira 댓글 → Github` | Jira 댓글을 GitHub 에 옮긴다 |
| `jira-status` | `<PREFIX> Jira 상태 → Github` | Jira 상태 범주 변경을 GitHub 이슈 열기/닫기에 반영한다 |

### 2-0. 값 파일 → 규칙 JSON (렌더 스크립트)

`files/jira-rules/values.example.json` 을 **저장소 밖**에 복사해 아래 17개를 채운다(✱ = 비워도 되는 칸).

| 값 이름 | 뜻 | 얻는 곳 |
|---|---|---|
| `PREFIX` | 규칙 이름 앞 구분 글자(예 `[AB]`) | 직접 정한다 |
| `SPACE` | Jira 스페이스 키 | 0절 `<SPACE>` |
| `PROJECT_ID` | 프로젝트 id(숫자) | 0-1절 |
| `CLOUD_ID` · `SITE` | cloudId · 사이트 주소(https:// 없이) | 0-1절 · 0절 `<SITE>` |
| `REPO` | GitHub `소유자/이름` | 0절 `<REPO>` |
| `ISSUE_TYPE_ID_BUG` · `_FEATURE` · `_TASK` | 스페이스의 유형 id 3개 | 0-1절 · 「기능」이 없으면 작업 id 두 번 |
| `JIRA_TYPE_BUG` · `JIRA_TYPE_FEATURE` | 유형 이름 — **대조표 `issueTypes.Bug` · `Feature` 와 같은 글자** | 0-1절 · 1-2절 |
| `START_DATE_FIELD` ✱ | 「시작 날짜」 필드 id — 스페이스에 없으면 **빈 글자**(렌더가 그 줄을 뺀다) | 0-1절 |
| `TRANSITION_DONE` · `TRANSITION_REOPEN` | 완료 · 다시 열기로 가는 전환의 **도착 상태 이름** | 0-1절 |
| `OWNER_ACCOUNT_ID` | 규칙 소유자(가져오는 사람)의 accountId | 0-1절 |
| `ACTOR_ACCOUNT_ID` | 「Automation for Jira」 앱 계정 id | 0-1절 |
| `SLACK_WEBHOOK_URL` ✱ | 권장: **비워 둔다**(값 파일이 저장소에 올라가면 안 된다) — 가짜 주소가 들어가고 Jira 화면에서 직접 붙여 넣는다 | Slack 「Incoming Webhooks」 |

```
node files/jira-rules/render-rules.mjs --values <값 파일> --out <출력 폴더>
```

- 값 형식이 틀리면(스페이스 키 · id · UUID · 저장소 · 계정 id 등) **이유를 적고 멈춘다**. 모르는 이름(오타)도 잡는다.
- 성공하면 `<SPACE>-github-to-jira.json` 등 5개가 나온다 — 모두 **꺼짐**, 범위 = 그 프로젝트, 웹 요청은 7곳(URL = `https://api.github.com/repos/<REPO>/actions/workflows/issue-sync.yml/dispatches`).
- 스크립트가 **채우지 않는 것**(사람이 화면에서): 웹 요청 7곳의 `Authorization` = `Bearer <PAT>` · Slack 주소 · `github-to-jira` 규칙의 수신 웹후크 URL·암호(가져오면 새로 생긴다 → GitHub Secret) · 켜기.
- 자체 시험: `node files/jira-rules/render-rules.mjs --selftest` (예시 값으로 렌더해 스크립트·템플릿이 맞는지만 본다).
- 규칙 구조를 고쳤다면 기준 상품의 내보내기에서 템플릿을 다시 만든다 — `files/jira-rules/maintainers/make-templates.mjs`(비밀값 · 상품 값이 남으면 실패한다).

### 2-2. 바꾸지 않는 칸
`hierarchyLevel = 0/1` 조건(일반 단 = 0 · 에픽 = 1 — **스페이스에서 에픽이 레벨 1 인 구성이어야 함**, 4절 가정) · 웹 요청 본문 JSON(`inputs` 키 10개) · 규칙 구조 · `jira-created` 규칙 트리거/조건.

## 3. 토큰 · Secret 전수

| 이름 | 어디에 | 값 만드는 곳 | 권한 |
|---|---|---|---|
| `<SECRET_URL>` · `<SECRET_TOKEN>` | **GitHub 저장소 Repository secrets**(Environment ✕) | Jira `github-to-jira` 규칙 수신 웹후크 | — |
| Jira→GitHub PAT | Jira 규칙 7곳 숨김 헤더 | Fine-grained PAT · Resource owner = 저장소 소유 조직 · **저장소 하나만** · **Actions: Read and write 하나만** | 이 토큰은 같은 저장소의 다른 `workflow_dispatch` 워크플로(예: `release.yml`)도 부를 수 있다 — 수동 실행에 실제 배포 job 을 붙이지 않는다(운영 `release.yml` 은 dry-run 뿐) |

## 5. 이 표가 가정하는 구성 (다르면 먼저 시험)

- **저장소 1 ↔ Jira 스페이스 1** 만 확인됨.
- Jira: 스페이스에서 **에픽 = hierarchyLevel 1, 일반 업무 = 0, 하위 작업 = -1**, 업무 유형 이름이 한글/영문 어느 쪽이든 대조표와 규칙에 같게 적혀 있음.
- GitHub: 조직 저장소 + 이슈 유형(Type: Task · Bug · Feature)이 쓰이는 조직(거절되면 워크플로가 Type 없이 다시 만듦 — `issue-sync.yml` Create copy 단계).
- 한 Jira 스페이스에 저장소 N개 · 한 저장소에 스페이스 N개 · 에픽이 레벨 1 이 아닌 구성은 **미검증**이다.
