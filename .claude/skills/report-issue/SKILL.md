# AI스킬 이슈등록 — GitHub ↔ Jira 양방향

GitHub 이슈와 Jira 업무 항목은 **짝으로 양방향 동기화**된다(GitHub Actions `issue-sync.yml` · Jira 규칙 5개).
웹에서 한 화면만 고치면 반대쪽이 따라오는 것과 똑같이, 이 스킬도 **한쪽만 쓰고 반대쪽은 확인만** 한다.

| 하는 일 | 스킬이 쓰는 곳 | 반대쪽 |
|---|---|---|
| 등록 | 고른 **한 곳에만**(GitHub 또는 Jira) | 자동화가 사본과 짝 표시를 만든다 |
| 제목 · 본문 · 댓글 · 상태 · 담당 바꾸기 | 사용자가 **적은 번호 쪽만**(Jira 키 → Jira, `#번호` → GitHub) | 자동화가 따라 바꾼다 |

개발자는 GitHub 을, 그 밖의 사람(기획 · 설계 등)은 Jira 를 본다는 가정이다.

## 2. 꼭 지킬 것

1. **반대쪽은 만들지도 고치지도 않는다.** 사본 · 링크 · 수정 · 댓글 · 상태 · 담당의 반대쪽 반영은 자동화 몫이다.
   양쪽을 다 고치면 같은 변경이 두 번 오가고 순서가 엇갈려 값이 뒤집힐 수 있다. 반대쪽이 안 바뀌어도 대신 하지 않고 경고만 한다.
   예외 하나 — GitHub 계정이 없는 사람을 담당으로 넣는 것(웹에서도 Jira 에서만 된다, 4-⑤).
2. **질문은 `AskUserQuestion` 으로, 한국어로** 묻는다. 선택지마다 「고르면 무엇이 바뀌는지」 한 줄.
   🔴 **어떤 선택지에도 「(권장)」 을 붙이지 않는다** — 대화로 추정한 것은 첫 번째에 둘 뿐 글자로 권하지 않는다.
   진행 안내 · 미리보기 · 보고 · 중간 한 줄(「60초 뒤 다시 찾는다」 등)까지 **모두 한국어**.
3. **지어내지 않는다.** 근거 없는 칸은 비운다. 대화 · 파일로 **추정해 채운 칸**은 미리보기에 「추정」으로 표시한다.
   댓글 · 본문 **문구는 사용자가 준 그대로** — 문구 없이 「댓글 달아줘」 · 「멘션 달아줘」만 오면 무엇을 쓸지 묻는다.
4. **사용자가 읽어야 할 것(미리보기 · 보고)은 응답 글로** 쓴다 — 아래 「앱 화면 주의」.
5. **제목에 번호표(`[TEST1-n]` 등)를 넣지 않는다.** 제목 = 양식 앞말 + 한 줄 요약.
6. **「Claude」를 Jira · GitHub 어디에도 남기지 않는다** — 레이블 · 라벨 · 제목 · 본문 · 댓글 모두.
7. **본문은 조립기 결과 그대로** — 쉬운 말로 바꾸거나 칸을 더하고 빼지 않는다(GitHub 웹 양식과 같은 모양).
8. 한글이 든 파일(답변 JSON · 본문)은 **Write 도구**로 쓴다. heredoc · `python` 은 쓰지 않는다.
9. 대조표에 **이메일은 쓰지 않는다.** 이름은 `jiraOnly` 키(GitHub 계정 없는 사람 — 영문 · 한글)에만, `people` 의 이름은 그때그때 Jira 에서 읽는다.
10. 커밋 · push · PR 은 그때마다 묻는다. 커밋 규칙은 CLAUDE.md 「작성자 표기」(마지막 줄 `담당: <git config user.email>`, Claude 표기 금지).

**앱 화면 주의**

| 상황 | 하는 법 |
|---|---|
| 같은 응답에서 글 뒤에 `AskUserQuestion` | 그 글이 화면에 안 보인다 — 미리보기 확인은 4-⑥ 의 두 단계로 묻는다 |
| 데스크톱 앱 「다음 할 일」 상자(`wrap_up`) | **상자를 먼저 부르고, 그 뒤 마지막 글로** 쓴다(앞에 쓰면 짧은 요약으로 잘린다) · 상자가 없으면(VS Code) 그냥 마지막 글로 |
| 생각(thinking) 안의 글 | 사용자에게 보이지 않는다 — 미리보기 · 보고는 반드시 응답 글로 |
| 60초 기다리기 | 백그라운드 `node -e "setTimeout(()=>{},60000)"` — 전경 `sleep` 은 막혀 화면에 「실패」로 보인다 |

## 3. 설정 — 스킬에 값을 적지 않고 그때 읽는다

저장소 · Jira 사이트가 바뀌어도(예: DS-Bridge 에 같은 방식을 쓸 때) 스킬은 고치지 않는다.
🔴 **양식 · 대조표 · 조립기는 늘 `origin/main` 에서** 꺼내 읽는다 — 작업 트리는 옛 브랜치일 수 있다.
`git fetch origin` 뒤 `git show origin/main:<경로>` 를 스크래치에 쓴다(Git Bash 는 앞에 `MSYS_NO_PATHCONV=1`).

| 항목 | 읽는 곳 |
|---|---|
| GitHub 저장소 `<저장소>` · `<저장소 이름>` | **`git remote get-url origin`** 에서 `<소유자>/<이름>` — 예 `nz-sdk/ai_skills` · `ai_skills`. 모든 `gh` 에 `-R <저장소>`. 🔴 `gh repo view` 로 정하지 않는다(원격이 둘이면 `upstream` 을 고른다) |
| Jira 사이트 | 대조표 `jira.cloudId`(MCP `cloudId`) · `jira.site`(링크 `https://<site>/browse/<키>`) |
| 양식 | `.github/ISSUE_TEMPLATE/*.yml` (`config.yml` 제외) |
| 대조표 | `.github/github-jira-map.yml` |
| 본문 조립기 | `node .github/scripts/issue-body.mjs <양식 yml> <답변 json> <본문 md>` |
| Jira 시작 날짜 칸 | 대조표 `spaces.<키>.startDateField`(값 `yyyy-MM-dd`) — 없는 스페이스는 넣지 않는다 |
| 영역 판정에서 세지 않는 폴더 | 대조표 `screenScanExclude` |
| 임시 파일 | 세션 스크래치 폴더(저장소 안에 두지 않음) |

| 양식 → | 읽는 곳 |
|---|---|
| 제목 앞말 · GitHub Type · 고정 라벨 | 양식 yml `title` · `type` · `labels` |
| Jira 업무 유형 | 대조표 `spaces.<키>.issueTypes.<Type>`, 없으면 `default` |

| 대조표 칸 | 내용 |
|---|---|
| `people` | GitHub 아이디 → `jiraAccountId` · `roles`(designer · developer · planner · product-designer, 여러 개) |
| `jiraOnly` | GitHub 계정 없는 사람. **키는 이름(영문 · 한글)** — GitHub 에서는 `<키>(Jira)` 로 보인다(예 `홍길동(Jira)`). 칸은 `people` 과 같음 |
| `spaces` | Jira 스페이스 키 → `issueTypes` · `default` |
| `areas` | 영역 → `space` · `screens`(화면 폴더) · `designers` · `developers` |

**사본 표시** — 자동화가 사본에만 붙인다(원본에 붙이면 자동화가 반대쪽으로 보내지 않는다).

| 어디 | 사본 표시 |
|---|---|
| GitHub | 제목 `[JIRA <키>]` · 라벨 `jira` · 작성자 `github-actions` · 맨 아래 출처 · 끝 `<!-- jira:<키> -->` |
| Jira | 요약 `[GH #n]` · 레이블 `github` · `gh-<저장소 이름>-<번호>` · 맨 아래 출처 |
| GitHub 원본 | 보이는 출처 없이 끝에 `<!-- jira:<키> -->` 만(짝 찾기용) |

### 0. 준비 점검 — 질문 없음

| 확인 | 방법 | 안 되면 |
|---|---|---|
| Jira 계정 | `atlassianUserInfo` | 「Jira」 를 빼고 재로그인을 알린다 |
| GitHub 계정 · 쓰기 권한 | `gh api user --jq .login` · `gh api repos/<저장소> --jq .permissions.push` | 「GitHub」 을 뺀다 |
| 내 역할 | 대조표 `people` · `jiraOnly` 의 `roles` | 「알 수 없음」 |

무엇을 뺐는지 한 줄로 알린다. 둘 다 빠지면 멈추고 이유를 알린다.

### ① 양식

- 양식 `name` · `description` 을 선택지로, 대화로 맞는 양식을 첫 번째에.
- 고른 양식에서 `title`(앞말) · `type` · `labels` · `body` 칸(id · label · 필수 · options · 기본 value)을 읽는다.

### ② 칸 채우기

- 대화 · 작업 내용(감사 문서 · 원천 대조 결과 등)으로 채우고, **비어 있는 필수 칸만** 묻는다.
- dropdown 은 양식 options 그대로(`multiple: true` 면 `multiSelect` · 답변 JSON 배열), 자유 입력은 「Other」로 받는다.
- **제목**: 양식 앞말 + 한 줄 요약. 예 `bug: 거래처등록 — 조회조건 거래처구분 선택이 저장되지 않음`.

**화면 → 영역** (④ · ⑤ 에 쓴다)

1. 칸 「화면」(한글 이름)을 화면 폴더에서 센다: `grep -rc "<화면명>" src/screens/<폴더>` 합계. **`screenScanExclude` 폴더는 세지 않는다.**
2. 가장 많은 폴더가 **3회 이상 · 둘째의 2배 이상**이고 대조표 `areas.*.screens` 에 있으면 그 영역.
3. 아니면 **「영역 밖」** — 추정 영역을 기본값으로 내놓지 않는다. 후보 폴더가 있으면 「이 화면 폴더가 맞나요?」로 묻는다.

### ②-0 상위 에픽 — 화면 이름으로 찾는다

스페이스는 ④ 의 기본값(화면 영역의 `space` · 스페이스가 하나면 그것)으로 찾고, ④ 에서 다른 스페이스를 고르면 다시 찾는다.
🔴 **상위 에픽은 필수다** — GitHub · Jira 어느 쪽에 올리든 에픽 없이 등록하지 않는다(웹 양식도 필수 칸).
화면 에픽이 없는 일(정리 · 설정 · 문서)은 **공통 에픽** 키를 쓴다.

아래 `<화면>` = 칸 「화면」(버그 · 기능) 값, 「화면」 칸이 없는 「일반 작업」은 칸 **「대상」** 값(적힌 그대로).
`<다듬은 화면>` = `<화면>` 에서 띄어쓰기와 끝의 「화면」 · 「메뉴」 를 지운 값(예 「주문 등록 화면」 → 「주문등록」).

```text
searchJiraIssuesUsingJql  (fields: summary · status · created)
project = <스페이스> AND hierarchyLevel = 1 AND statusCategory != Done
  AND (summary ~ "<화면>" OR summary ~ "<화면>*" OR summary ~ "<다듬은 화면>" OR summary ~ "<다듬은 화면>*")
  ORDER BY created DESC   (최대 10건)
```

- 🔴 **이름 전체**로 찾고, **적힌 값과 다듬은 값을 함께** 넣는다 — Jira 는 띄어쓰기를 낱말 경계로 보고 한글 낱말은 쪼개지 않아
  「주문 등록」 · 「주문등록 화면」 · 「주문」 만으로는 「주문등록」 에픽을 못 찾거나 여럿을 찾는다. 띄어쓰기가 든 에픽 이름도 있어 다듬은 값만 넣지 않는다.
- 🔴 **에픽 키 검사** — 사람이 적은 키는 쓰기 전에 `getJiraIssue <키>` 로 ① 있는지 ② 에픽(`hierarchyLevel` 1)인지 ③ 등록할 스페이스의 키인지 본다.
  대상: 요청에 적은 키(「TEST1-6 아래로」 — 이때는 검색하지 않는다) · 아래 표의 「Other」 에 적은 키 · 5-2 상위 바꾸기 · GitHub 본문 「상위 에픽 키」 칸 수정.
  하나라도 아니면 **쓰지 않고** 「<키> 는 <없는 번호 | 에픽이 아님 | 다른 스페이스 키> 입니다」 를 알린 뒤 0건 선택지로 다시 묻는다.
  검색 결과에서 고른 에픽은 이미 확인된 것이라 다시 보지 않는다.

| 찾은 수 | 하는 일 |
|---|---|
| 1건 | **묻지 않는다** — ⑥ 미리보기 「상위」에 넣고 「⚠️ 추정한 칸」에 올린다. 「수정할게요」로 바꿀 수 있다 |
| 2건 이상 | 묻는다 — 선택지 = 에픽마다 `<키> <요약>`(설명 칸 「만든 날 yyyy-MM-dd · <상태>」). 요약이 `<다듬은 화면>` 과 **글자까지 같은** 에픽을 첫 번째로. 4건을 넘으면 앞 3건 + 「다음 후보」 로 이어서 묻는다 |
| 0건 | 묻는다 — 열린 에픽 전체(`project = <스페이스> AND hierarchyLevel = 1 AND statusCategory != Done` · 100건을 넘으면 나눠 받는다)에서 요약이 `<다듬은 화면>` 과 **두 글자씩 가장 많이 겹치는 4건**을 선택지로 · 「Other」에 에픽 키 직접 입력(공통 에픽 키 포함) — 위 「에픽 키 검사」 를 거친다 |

- 「상위 없음」 선택지는 두지 않는다. 사용자가 끝내 키를 주지 않으면 등록하지 않고 멈춘다(무엇이 막혔는지 한 줄 보고).

- 스킬은 **에픽 · 하위 작업을 만들지 않는다**(에픽은 기획자가 Jira 에서 만든다 · 동기화 대상 아님). 「에픽 만들어줘」가 오면 그렇다고 알리고 끝낸다.
- 예: 「주문등록」처럼 이름이 같은 에픽이 두 건 이상 나오면 — 묻는다.

### ②-1 중복 확인

```text
Jira   searchJiraIssuesUsingJql
       (상위가 있으면 먼저) project = <스페이스> AND parent = <에픽> AND statusCategory != Done ORDER BY created DESC   (최대 5건)
       project = <스페이스> AND hierarchyLevel = 0 AND statusCategory != Done AND text ~ "<화면>" AND created >= -30d ORDER BY created DESC   (최대 5건)
GitHub gh issue list -R <저장소> --state open --search "<화면> in:title" --json number,title,url --limit 5
```

- `hierarchyLevel = 0` — 에픽 · 하위 작업은 같은 건 후보가 아니다.

같은 건이 있으면 **후보를 버튼으로** 고르게 한다 — 후보를 질문 글에만 늘어놓지 않는다(「기존 건 사용」 을 눌러도 어느 건인지 고를 수 없었다).

- 후보 한 건 = Jira 키와 GitHub 번호의 **짝 하나**(5-1 짝 찾기로 묶는다 — `TEST1-12` 와 `#34` 이 짝이면 버튼 하나).
  - 글자: `<키> = #<번호> · <요약>`(짝이 없으면 있는 쪽만) · 설명 칸: 「<유형> · <상태> · 담당 <이름 | 없음>」.
  - 순서: 최근에 만든 것부터.
- 🔴 선택 질문은 한 번에 **선택지 4개**까지다(⑤ 와 같은 방식).
  - 후보 **3건 이하** → 한 번에 묻는다 — 선택지 = 후보마다 버튼 + **새로 등록**.
  - 후보 **4건 이상** → 두 단계 — ②-1-1 「같은 일로 보이는 건이 <n>건 있습니다. 그중 하나를 쓸까요?」 **기존 건 중에서 고르기** · **새로 등록**(설명 칸에 후보 키 · 번호를 줄여 적는다).
    ②-1-2 기존 건이면 후보 버튼 — 4건을 넘으면 앞 3건 + 「다음 후보」 로 이어서 묻는다.
- 기존 건을 고르면 **아무것도 쓰지 않고**(댓글 · 멘션 포함) 그 건의 키 · 번호 · 링크 · 상태 · 담당만 보고한다.

### ③ 등록할 곳 — 한 곳만

- 선택지 **GitHub** · **Jira**(0 에서 뺀 것은 안 보임) — 늘 이 순서. 「둘 다」는 없다.
- 🔴 **「(권장)」 을 붙이지 않고 역할로 미리 고르지도 않는다** — 설명 칸에 「<쪽>에 원본이 생기고 반대쪽 사본은 1분 안에 자동으로 생긴다」 만 적는다.

### ④ 스페이스

- 대조표 `spaces` 의 키 — 기본값은 화면 영역의 `space`, 영역 밖이면 첫 번째. **하나면 묻지 않는다.**
- Jira 업무 유형은 양식 `type` → `issueTypes`(없으면 `default`). GitHub 에 올릴 때도 미리보기에 「Jira 사본이 생길 곳」으로 보인다.

### ⑤ 담당자 — 기본값 없음 · 모든 사람을 버튼으로

- 🔴 어떤 선택지에도 「(권장)」을 붙이지 않는다.
- 사람: 대조표 `people` · `jiraOnly` + **지정 안 함**.
  - 글자: Jira 에서 읽은 **「이름(역할)」** — 역할이 여럿이면 「이름(역할 · 역할)」.
  - 설명 칸: GitHub 아이디 — 없으면 「Jira만」 · 저장소 담당이 안 되면 「GitHub 담당 불가」.
  - 순서: 화면 영역의 `designers` · `developers` 를 앞에 둔다. 순서만 바꾸고 기본값으로 고르지 않는다.
- 🔴 선택 질문은 한 번에 **선택지 4개**까지다 — 「Other」 에 번호를 적게 하지 말고 **모든 사람이 버튼으로 보이게** 묻는다.
  - 사람 + 「지정 안 함」이 **4개 이하** → 한 번에 묻는다.
  - **넘으면 두 단계** — ⑤-1 「어느 쪽인가요?」 선택지 = 역할 묶음(대조표 `roles` 의 첫 역할: 개발자 · 프로덕트 디자이너 · 기획 · 설계 …, 설명 칸에 「<n>명 — 이름, 이름 …」) + **지정 안 함**.
    묶음이 4개를 넘으면 사람 수가 적은 묶음부터 합쳐 「그 밖(<역할> · <역할>)」 하나로.
    ⑤-2 고른 묶음의 사람만 버튼 — 4명을 넘으면 앞 3명 + 「다음 명단」 으로 이어서 묻는다.
- 명단 밖 사람은 Other 에 적은 이름으로 `lookupJiraAccountId` 후보를 보인다. 지정 안 함이면 담당 없이(스페이스 기본 담당자가 들어갈 수 있다).

담당은 **등록하는 쪽에만** 넣는다(반대쪽은 자동화가 대조표로 맞춘다).

| 등록할 곳 | 넣는 법 |
|---|---|
| Jira | `assignee_account_id` = 그 `jiraAccountId` |
| GitHub | `people` 에서 GitHub 아이디를 찾아 ⑦ 의 `assignees`. 먼저 `gh api repos/<저장소>/assignees/<아이디>`(204 가능 / 404 불가) — 불가면 미리보기에 「GitHub Assignee: 없음 — 저장소 권한 없음」을 보이고 뺀다 |
| GitHub + `jiraOnly` 담당 | GitHub 칸에는 넣을 수 없다 → **⑧ 에서 Jira 사본을 찾은 뒤 사본 담당자 칸에 직접** 넣는다(`editJiraIssue`). 미리보기 담당 줄은 「<이름(역할)> — GitHub 칸은 비고, Jira 사본 담당으로 넣음」 |

### ⑥ 미리보기

1. 답변 JSON(칸 id → 값, dropdown 은 선택지 글자 그대로)을 스크래치에 Write.
2. `node <스크래치>/issue-body.mjs <스크래치>/<양식>.yml <답변> <스크래치>/body.md` — 본문은 셋째 인자 파일로 받는다. `>` 리디렉션은 PowerShell 5.1 에서 UTF-16 으로 저장돼 한글이 깨진다.
   종료 코드가 3 · 4 · 5 면 ②로 돌아간다 — 3 없는 칸 · 4 필수 누락 · 5 선택지 밖.
3. 본문에 넣지 않는 것:

   | 넣지 않는 것 | 이유 |
   |---|---|
   | 「출처」 블록 · `<!-- jira:<키> -->` | 자동화가 넣는다 |
   | 작성자 · 등록 시각 줄 | GitHub 작성자 · Jira 보고자 · 시작 날짜 칸으로 남는다 |
4. Jira 시작 날짜 = 오늘(한국 시간): `node -e "console.log(new Date().toLocaleString('sv-SE',{timeZone:'Asia/Seoul'}).slice(0,10))"`

**카드** — 인용 블록 하나. 위는 항목 표, 아래는 본문 전체(`body.md` 줄마다 `> `).

```markdown
> **등록 미리보기** · <Jira <스페이스> | GitHub <저장소>>
>
> | 항목 | 내용 |
> |---|---|
> | 제목 | <제목> |
> | 유형 | <Jira 업무 유형 | GitHub Type> |
> | 레이블 | <양식 labels — 없으면 「없음」> |
> | 담당자 | <이름(역할) | 할당되지 않음> |
> | 상위 | <에픽 키 · 요약> — 필수. GitHub 에 올리면 양식 칸 「상위 에픽 키」 로 가서 Jira 사본 상위가 된다 |
> | 시작 날짜 | <yyyy-MM-dd — Jira 만> |
> | 반대쪽 | <GitHub | Jira> 사본이 자동으로 생긴다 |
> | ⚠️ 추정한 칸 | <칸 이름 — 확인 필요> (없으면 줄을 뺀다) |
>
> ---
>
> <본문 전체>
```

**두 단계로 묻는다** — 카드와 질문을 한 응답에 두면 카드가 안 보이고, 「다음 할 일」 상자는 버튼이 1 ~ 2개뿐이다.

| 단계 | 이 응답에서 할 일 |
|---|---|
| ⑥-1 | (상자가 있으면) 상자 — `ask` 「미리보기를 확인하셨나요?」 · 버튼 `{"label":"선택하기","message":"미리보기 확인했어 — 선택지 보여줘"}` · `blocked: true` → 카드를 마지막 글로 쓰고 끝. 상자가 없으면 카드 아래 「선택하려면 「선택」이라고 답해 주세요.」 |
| ⑥-2 | 다음 말을 받으면 **글 없이** `AskUserQuestion` — 「위 미리보기대로 등록할까요?」 **등록 · 수정할게요 · 취소** |

등록 → ⑦ · 수정할게요 → 고칠 것을 받아 해당 단계로(고친 뒤 ⑥-1 부터) · 취소 → 아무것도 쓰지 않음. ⑥-1 에서 「등록」 · 「취소」를 바로 적으면 그대로 따른다.

### ⑦ 등록 — 고른 한 곳에만

**GitHub**

🔴 **REST 한 번으로 만든다 — `gh issue create` 를 쓰지 않는다.** `gh issue create --type` 은 이슈를 먼저 만들고 Type 을 2초 뒤 따로 붙여,
동기화가 받는 `opened` 이벤트에 Type 이 없다 → Jira 사본이 대조표 기본값(작업)으로 생긴다.

1. `<스크래치>/meta.json` 을 Write — `{"title":"<제목>","type":"<양식 type>","labels":[<양식 labels>],"assignees":[<⑤ 에서 확인한 GitHub 아이디>]}`(빈 칸은 뺀다).
2. `<스크래치>/payload.cjs` 를 Write(한 번만):

   ```js
   // node payload.cjs <meta.json> <body.md> <payload.json> [빼고 만들 칸…]
   const fs = require('fs');
   const [meta, body, out, ...drop] = process.argv.slice(2);
   const read = f => fs.readFileSync(f, 'utf8').replace(/^﻿/, '');
   const p = JSON.parse(read(meta));
   p.body = read(body);
   for (const k of drop) delete p[k];
   for (const k of ['labels', 'assignees']) if (Array.isArray(p[k]) && !p[k].length) delete p[k];
   fs.writeFileSync(out, JSON.stringify(p));
   ```
3. 만든다:

   ```text
   node <스크래치>/payload.cjs <스크래치>/meta.json <스크래치>/body.md <스크래치>/payload.json
   gh api repos/<저장소>/issues --method POST --input <스크래치>/payload.json --jq .number
   ```

- 양식 칸 「상위 에픽 키」(id `epic`)는 ②-0 의 에픽 키로 채운다 — 동기화가 이 칸을 읽어 Jira 사본 상위로 넣는다.
- 라벨은 양식 `labels` 만 — **`jira` 는 붙이지 않는다**(사본 표시). 저장소에 없는 라벨은 빼고 경고(새로 만들지 않음).
- 실패하면:
  - **422**(검증 실패) — 요청 전체가 거절된 것이라 이슈는 **생기지 않았다**. 오류의 `field`(`type` · `assignees` · `labels`)만 빼고(`payload.cjs … type` 처럼 넷째 인자부터) **한 번만** 다시 만든다. 보고에 「Type 을 붙이지 못함」 등 경고.
  - 시간 초과 · 연결 끊김처럼 결과를 모르면 🔴 바로 다시 만들지 않는다 — `gh issue list -R <저장소> --author @me --state all --limit 5 --json number,title,createdAt` 에서 **같은 제목 · 2분 안** 이슈를 찾아 있으면 그것을 쓴다.
- JSON 은 늘 파일(`--input`)로 넘긴다 — PowerShell 5.1 은 native 명령의 JSON 인자 따옴표를 깨뜨린다. `node -e` 인라인에 본문을 넣지 않는다.

**Jira** — `createJiraIssue`(`contentFormat: "markdown"`)

| 칸 | 값 |
|---|---|
| `projectKey` · `issueTypeName` | ④ |
| `summary` · `description` | 제목 · 본문 |
| `assignee_account_id` | ⑤(지정 안 함이면 뺀다) |
| `parent` | ②-0 의 에픽 키(필수) — 예 `"TEST1-6"` |
| `additional_fields` | `{"labels": [<양식 labels>], "<startDateField>": "<오늘>"}` — **`github` 은 넣지 않는다**(사본 표시) |

실패하면 멈추고 오류를 그대로 보인다.

**설계 확인 필요 = 예(버그 양식)** — 영역 설계자를 **실제 멘션**으로(이름 글자만으로는 알림이 안 간다). 댓글은 **등록한 쪽에 하나만** — 반대쪽은 자동화가 옮긴다.

| 등록한 곳 | 방법 | 반대쪽 모양 |
|---|---|---|
| Jira | `addCommentToJiraIssue` · `contentFormat: "adf"` · mention 노드(아래), `people` · `jiraOnly` 설계자 모두 · 여럿이면 노드를 이어 댓글 하나로 | GitHub 사본에 `@<GitHub 아이디>` · `jiraOnly` 는 `<키>(Jira)` |
| GitHub | 댓글 하나 `설계 확인 요청: @<GitHub 아이디> …` — `people` 설계자 | Jira 사본에 실제 멘션. ⚠️ `jiraOnly` 설계자는 GitHub 에서 부를 수 없다 — 보고에 「<이름>은 Jira 에서 직접 확인 요청 필요」 |

```json
{"type":"doc","version":1,"content":[{"type":"paragraph","content":[
  {"type":"text","text":"설계 확인 요청: "},
  {"type":"mention","attrs":{"id":"<jiraAccountId>","text":"@<이름>"}}]}]}
```

Jira 지켜보기(watcher)는 MCP 도구가 없어 하지 않는다.

### ⑧ 확인 · 보고 — 질문 없음

**다시 읽은 값**으로 보고한다.

| 무엇 | 방법 |
|---|---|
| 등록한 쪽 | Jira `getJiraIssue`(요약 · 유형 · 보고자 · 담당 · 레이블 · 시작 날짜 · `parent`) / GitHub `gh issue view <m> --json title,author,assignees,labels,issueType,url` |
| 반대쪽 (GitHub 에 올림) | Jira JQL `labels = gh-<저장소 이름>-<m>` → 1건. GitHub 원본 끝에 `<!-- jira:<키> -->` 가 들어갔는지 |
| 반대쪽 (Jira 에 올림) | 5-1 「짝 찾기」 → `#m` · 라벨 `jira` · 출처 링크 |

- 등록 직후 **바로 한 번** 찾고(보통 10초 안), 없으면 60초 뒤 한 번 더. 두 번 다 없으면 **대신 만들지 않고** 「반대쪽 사본이 아직 없음 — 자동화 확인 필요」.
- ⑤ 의 「GitHub + `jiraOnly` 담당」이면 사본을 찾은 직후 사본 담당을 넣고 다시 읽는다. 사본이 없으면 넣지 못한 것을 경고한다.
- **GitHub 에 올렸으면** 사본을 찾은 직후 사본 `parent` 를 읽는다 — 자동화 「[AX_AI] Github -> Jira Issue」 가 양식 칸으로 넣는다.
  비었거나 ②-0 의 에픽과 다르면(자동화가 아직 상위를 넣지 않음 · 실패) `editJiraIssue` `fields: {"parent": {"key": "<에픽>"}}` 로 붙이고 다시 읽는다
  (담당과 같은 예외 — 상위는 Jira 에만 있다). 「[AX_AI] Jira 수정 -> Github Issue」 는 요약 · 설명 · 담당 변경에만 돌아 이 수정은 GitHub 으로 가지 않는다.
  사본이 없으면 「상위를 붙이지 못함 — Jira 에서 <에픽> 아래로 옮겨 주세요」.
- **GitHub 에 올렸으면 사본 유형**이 대조표 `issueTypes.<Type>` 과 같은지 본다. 다르면 「⚠️ Jira 사본 유형 <실제> ≠ <기대>」 — 자동으로 바꾸지 않고 Jira 에서 바꾸도록 알린다.
- 「설계 확인」 댓글이 반대쪽에 옮겨졌는지도 본다(없으면 경고만).
- 보고 모양: `✅ <등록한 쪽 번호> (<유형> · 담당 <이름> · 상위 <에픽 | ⚠️ 비어 있음>) → 사본 ✅ <반대쪽 번호> (<유형>) / ⚠️ 없음` + 각 링크 + 어긋난 값. 상위는 다시 읽은 Jira `parent` 값으로.

## 5. 바꾸기 · 후속 명령

### 5-1. 짝 찾기 (Jira 키 → GitHub 이슈)

위에서부터 찾고 처음 찾은 것을 쓴다. `--search` · `--label` 은 쓰지 않는다(검색 색인이 몇 초 늦어 방금 생긴 이슈를 못 본다).

| 순서 | 방법 | 맞는 경우 |
|---|---|---|
| 1 | Jira 레이블 `gh-<저장소 이름>-<m>` → `#m` | GitHub 에 먼저 올린 건 |
| 2 | GitHub 본문 `<!-- jira:<키> -->` — `gh issue list -R <저장소> --state all --limit 100 --json number,body` | GitHub 사본 · 짝 표시가 붙은 GitHub 원본 |
| 3 | GitHub 제목 `[JIRA <키>]` · `[<키>]` 로 시작 | GitHub 사본 |

셋 다 없으면 「GitHub 사본이 아직 없음 — 자동화 확인 필요」로 알리고 **만들지 않는다**.

### 5-2. 「<키 | #번호> … 바꿔줘」 — 제목 · 본문 · 댓글 · 상태 · 담당 · 상위

🔴 **적은 번호 쪽만 바꾼다** — `TEST1-12` 면 Jira 만, `#34` 이면 GitHub 만. 반대쪽은 5-5 「반영 확인」만.
번호가 없거나(「이 건 제목 바꿔줘」) 모호하면 묻는다. 상대 쪽 번호는 5-1 로 구한다.

| 바꿀 것 | Jira 키일 때 | `#번호` 일 때 | 반대쪽에 기대하는 값 |
|---|---|---|---|
| 제목 | `editJiraIssue` `summary` — 사본이면 앞 `[GH #n] ` 를 지킨다 | `gh issue edit -R <저장소> <n> --title` — 사본이면 앞 `[JIRA <키>] ` 를 지킨다 | 반대쪽 제목 · 사본 출처 줄의 제목도 새 것 |
| 본문 | 지금 설명을 읽어 말한 곳만 고쳐 `editJiraIssue` `description`(markdown) — 사본이면 맨 아래 「출처」를 지킨다 | 지금 본문을 읽어 고친 파일로 `--body-file` — 사본이면 「출처」, 모두 끝 `<!-- jira:<키> -->` 를 지킨다. **`### 상위 에픽 키` 칸이 바뀌면 아래 「상위」 줄대로** 처리한다(검사 → Jira 상위도 함께) | 고친 줄만 넘어가고 출처 · 표시는 안 넘어간다 |
| 댓글 | `addCommentToJiraIssue`(멘션은 adf mention 노드) | `gh issue comment --body-file`(멘션 `@<GitHub 아이디>`, `people` 만) | 「<이름> 님 … 댓글」 + 멘션은 대조표로(Jira → GitHub `@아이디` · `<키>(Jira)` / GitHub → Jira 실제 멘션) |
| 상태 | `getTransitionsForJiraIssue` → `transitionJiraIssue` | 「완료 · 닫아」 `gh issue close --reason completed` · 「할 일 · 다시 열어」 `gh issue reopen`. 「진행 중 · 검토 중」은 GitHub 에 없는 상태 — **Jira 키로 할까요?** 묻는다 | Jira 완료 ↔ GitHub 닫힘, 그 밖 ↔ 열림 |
| 담당 | `editJiraIssue` `assignee`(지정 안 함 `null`) | `gh issue edit --add-assignee` · `--remove-assignee`(`people` 의 GitHub 아이디) | 아래 표 |
| 상위 | ②-0 「에픽 키 검사」 → 맞으면 `editJiraIssue` `parent: {"key": "<에픽>"}`. 짝이 **GitHub 원본**(Jira 가 사본)이면 GitHub 본문 「상위 에픽 키」 칸도 새 키로 고친다 — 상위를 비우지는 않는다(필수 · 요청이 오면 알리고 옮길 에픽을 묻는다) | 「상위 바꿔줘」 든 본문 「상위 에픽 키」 칸 수정이든 ②-0 「에픽 키 검사」 → 맞으면 ① GitHub 본문 칸을 새 키로 고치고 ② 5-1 로 찾은 **Jira 짝의 상위도** 같은 키로 바꾼다. 틀리면 **본문도 고치지 않는다** | GitHub 본문 「상위 에픽 키」 = Jira 상위. 자동화도 한쪽 변경을 반대쪽으로 옮기지만 늦을 수 있어 스킬이 양쪽을 바로 맞춘다 |

- 문구는 사용자가 준 그대로, 없으면 묻는다. 담당자 이름만 오면 대조표 · Jira 에서 찾고, 없거나 둘 이상이면 4-⑤ 처럼 묻는다.
- 이미 그 값이면 바꾸지 않고 「이미 <값>」으로 보고한다.
- **예외** — GitHub 계정 없는 사람을 `#번호` 로 담당 지정: GitHub 에는 넣을 수 없다 → 「Jira 쪽(<키>)에서 지정할까요?」 동의하면 Jira 짝에.
- **예외** — 상위 에픽은 양쪽을 스킬이 맞춘다(위 표 「상위」). 자동화도 GitHub 본문 키 ↔ Jira 상위를 옮기지만 Jira 자동화 실행이 몇 시간씩 밀릴 수 있어 그동안 본문 키와 실제 상위가 어긋난다. 같은 값을 다시 쓰므로 겹쳐도 바뀌는 것은 없다.

| 담당으로 고른 사람 | 반대쪽 담당 |
|---|---|
| `people` (저장소 담당 가능) | Jira ↔ GitHub 아이디 |
| `people` (저장소 권한 없음) | GitHub 은 **비어 있음** — 자동화가 경고만 남긴다(보고에 그대로) |
| `jiraOnly` · 명단 밖 · 지정 안 함 | GitHub 은 비어 있음 |

### 5-3. 「<키> 작업 시작해줘」

1. `getJiraIssue <키>` → 요약 · 유형 · 담당 · 레이블 · 설명. GitHub 짝은 5-1 → `gh issue view <m>`(없으면 알리고 **만들지 않는다**).
2. 브랜치 이름을 묻는다: **`<type>/<키>-<영문 설명>`** / 직접 입력 — 버그 `fix` · 기능 `feat` · 작업 `docs` 또는 `chore`. worktree 로 만든다:

   ```text
   git fetch origin
   git worktree add --no-track <worktree 폴더> -b <브랜치> origin/main
   ```

   - 🔴 `--no-track` 을 빼지 않는다 — 빼면 브랜치가 `origin/main` 을 따라가 `git push` 가 main 을 겨눈다. 처음 push 는 `git push -u origin <브랜치>`.
   - worktree 폴더는 묻는다: `<저장소 상위>/wt/<키>` / 세션 스크래치(임시).
3. 「Jira 를 진행 중으로 바꿀까요?」 → 진행 중 전환. **Jira 만** — GitHub 은 열림 그대로(닫혀 있었다면 자동화가 다시 연다).
4. 5-5 로 확인해 보고한다.

### 5-4. 「<키> 완료 보고해줘」

웹과 같은 순서 — PR 이 이슈를 닫고(`Closes #`), 닫힘이 Jira 「완료」로 넘어가고, 결과 댓글은 한 번.

1. GitHub 짝 이슈(5-1)와 그 이슈를 닫는 PR 을 찾는다 — 이슈 `closedByPullRequestsReferences` · `gh pr list -R <저장소> --state all --json number,state,mergedAt,url,headRefName` 중 `headRefName` 에 `<키>`.
2. **머지된 PR 이 없으면 완료 처리하지 않는다** — 「PR #n 이 머지되지 않았습니다(닫힘 / 열림)」 보고 후 끝. (PR 없이 상태만 바꾸려면 5-2 「상태」.)
3. 상태 — **Jira 를 직접 완료로 바꾸지 않는다.** GitHub 이 이미 닫혔으면 아무것도 안 하고 5-5 로 Jira 완료를 본다. 열려 있으면 「GitHub 이슈를 닫을까요?」 **닫기** / 닫지 않음 → 닫기면 **GitHub 만** 닫는다.
4. 결과 댓글 — 「결과 댓글을 남길까요?」 **Jira 에 남김** / 남기지 않음. 내용 = PR 제목 · 요약 + 링크. **Jira 에 한 번만**(GitHub 에는 자동화가 옮긴다).
5. 5-5 로 GitHub 닫힘 · Jira 완료 · 양쪽 댓글을 확인해 보고한다.

### 5-5. 반영 확인 (5-2 ~ 5-4 공통)

- 바꾼 직후 한 번 → 안 바뀌었으면 60초 뒤 한 번 더. **읽어서만** 본다.
- 그래도 다르면 「자동화 반영 안 됨 — <무엇이 어떻게 다른지>」 경고 + 힌트 `gh run list -R <저장소> --workflow issue-sync.yml --limit 3`(GitHub → Jira 는 job `from-github`, Jira → GitHub 은 `from-jira`).
- 보고 모양: `✅ <바꾼 쪽> <무엇> → 반대쪽 ✅ 반영 / ⚠️ 안 됨` + 각 링크.

## 6. 규칙의 이유

| 규칙 | 이유 |
|---|---|
| 한쪽만 쓰고 반대쪽은 확인만 · 적은 번호 쪽만 | 양쪽을 다 고치면 같은 변경이 두 번 오가고 순서가 엇갈려 값이 뒤집힌다. 웹에서 연 화면만 고치는 것과 같게 한다 |
| 「완료 보고」는 Jira 를 직접 완료로 바꾸지 않음 | PR 이 이슈를 닫으면 자동화가 같은 전환을 보낸다 — 직접 바꾸면 두 번이 된다 |
| 저장소는 `origin` 에서 | `gh repo view` 는 원격이 둘이면 `upstream` 을 골라 다른 저장소에 쓸 수 있다 |
| ⑦ GitHub 은 REST 한 번으로 | `gh issue create --type` 은 Type 을 따로 붙여 동기화가 받는 `opened` 이벤트에 Type 이 없다 → Jira 사본이 기본 유형으로 생긴다 |
| 결과를 모르는 실패는 바로 다시 만들지 않음 | 이슈가 이미 생겼을 수 있어 다시 만들면 중복된다. 422 는 요청 전체가 거절된 것이라 한 번 다시 만든다 |
| ②-0 상위 에픽은 필수 · 「상위 없음」 없음 | 웹 양식 「상위 에픽 키」 도 필수 칸이다 — 웹 양식 · 스킬(GitHub · Jira) 어느 길로 등록해도 같은 기준이다. 화면과 무관한 일은 공통 에픽 |
| ②-0 에픽은 이름 전체로 · 적힌 값 + 다듬은 값 · 1건이어도 미리보기에서 확인 | Jira 는 한글 낱말을 쪼개지 않는다 · 같은 이름의 에픽이 둘 이상 있을 수 있다 · 앞부분이 겹치는 이름이 있다 · 지어내지 않는다 |
| ②-0 일반 작업은 「대상」 칸으로 | `task.yml` 에는 「화면」 칸이 없다 — 건너뛰면 일반 작업은 상위를 못 찾는다 |
| 자동화 규칙은 상위를 필수로 두지 않음 | 상위가 없다고 동기화를 멈추면 반대쪽 사본이 아예 안 생긴다. 필수는 입구(양식 · 스킬)에서 받고, 빠진 건은 `project = TEST1 AND hierarchyLevel = 0 AND parent is EMPTY` 로 찾는다 |
| 에픽 · 하위 작업은 만들지 않음 | 에픽은 동기화 대상이 아니다 |
| 사람이 적은 에픽 키는 모두 검사 · 상위를 바꾸면 GitHub 본문 칸과 Jira 상위를 함께 | 자동화도 틀린 키면 Jira 사본을 만들지 않고(수정이면 상위를 바꾸지 않고) 슬랙으로 알리지만, 그때는 이미 GitHub 이슈가 올라간 뒤다. 스킬은 Jira 를 읽을 수 있어 쓰기 전에 막고, 오타를 고칠 때도 본문 키와 실제 상위가 어긋나지 않게 양쪽을 바로 맞춘다 |
| 문구는 묻는다 · 칸은 지어내지 않는다 | 사용자가 하지 않은 말이 이슈 · 댓글에 남는다 |
| ②-1 기존 건이면 댓글도 달지 않음 | 같은 티켓에 본문 댓글 · 멘션 댓글이 겹쳐 달린다 |
| 영역 판정에서 `screenScanExclude` 제외 | 메뉴 등록부처럼 화면 이름만 모아 둔 폴더까지 세면 영역을 잘못 본다 |
| ⑤ 4명을 넘으면 역할로 두 단계 | 선택 질문은 선택지가 4개까지라, 한 번에 물으면 4번째 이후 사람은 버튼이 없어 「Other」 에 번호를 적어야 했다 — 모든 사람을 버튼으로 고르게 한다 |
| ②-1 후보를 버튼으로 · 4건 이상이면 두 단계 | 후보를 질문 글에만 늘어놓으면 「기존 건 사용」 을 골라도 어느 건인지 정할 수 없었다 |
| 「(권장)」 표시 없음 · ③ 은 역할로 미리 고르지 않음 | 권장 표시가 사용자 판단을 한쪽으로 끈다. 추정은 순서로만 드러낸다 |
| ⑤ GitHub 지정 가능 여부를 미리 봄 | 저장소 권한 없는 아이디는 담당이 될 수 없다 — 미리 빼야 등록이 그 때문에 실패하거나 조용히 빠지지 않는다 |
| ⑥ 카드 · 두 단계 질문 | 한 줄 요약은 읽기 어렵고, 카드와 질문을 한 응답에 두면 카드가 안 보인다 |
| ⑦ 멘션은 실제 멘션 노드 | 이름 글자만 적으면 알림이 가지 않는다 |
| 시작 날짜는 `node` 로 | Windows Git Bash 의 `TZ=Asia/Seoul date` 는 UTC 를 낸다 |
| 한 곳에만 등록 · 원본 제목에 번호표 없음 · Claude 표시 없음 | 팀 합의 |
